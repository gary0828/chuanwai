# 外部 PRD 对照与借鉴分析

> **输入**：`学科机构_全学段教务管理平台_PRD_v1.0.docx`（外部 AI 产出，V1.0，23 章 / 207 个节点 / 32 张表）
> **对照物**：本项目实际 schema（v20）、路由、页面，以及 `docs/08-参考/教务功能补全分析-2026-09-23.md`（本会话前一份报告）
> **目的**：判断这份 PRD 里**哪些值得借鉴、哪些必须改造、哪些与本项目已拍板边界冲突**
> **性质**：分析结论，**不改 ROADMAP、不动代码**；是否立项由用户拍板。

---

## 0. 结论摘要（先看这个）

| # | 结论 | 依据 |
|---|---|---|
| 1 | 这是一份**质量不差、但目标不同**的 PRD。它描述的是「**集团/多校区 · K12 全学段 · 含家长端 · 给 AI 平台当数据底座**」的产品；本项目是「**单校区自用 · 纯员工端 · 200–500 学员**」的 CRM。两者在 **4 条已拍板决策上正面冲突** | §1 |
| 2 | ★★ **最重要的价值：它独立印证了我们昨天报告的 5 项判断** —— 尤其 `lesson_instance_id`（课次实例）与「任课教师」维度。**两个独立分析指向同一结论，优先级应上调** | §2 |
| 3 | **它的 13 个一级模块里，12 个我们有对应**（含薄实现）。**整体空缺的模块只有一个：数据中心**（数据字典 / 指标口径 / 数据质量 / 对外数据服务） | §3 |
| 4 | 值得借鉴的**功能**其实不多（我们覆盖率不低），真正值钱的是它的**第 7、8、13 章**——数据建模、数据治理、隐私合规基线 | §4 |
| 5 | 明确**不采纳** 7 类。其中最要警惕的是：**若不加判断地按它建设，会把一个 200–500 学员的单校区系统做成集团 ERP**（多校区 + 数仓 + 8 角色 + 家长端） | §6 |
| 6 | 这份 PRD 自身有 **6 处产品级缺陷**（最严重的是：把"单校区还是多校区""家长端形态"这类**决定整个架构的前提**留到第 21 章当"待确认"，而数据模型已在第 7 章按多校区画好） | §7 |

**一句话建议**：**借鉴它的"数据观"，拒绝它的"产品观"。**

## 1. 定位对照：一切分歧的根源

> 先看这张表，再看后面的"可借鉴"。很多看似"我们缺的功能"，其实是"它面向另一种机构"。

| 维度 | PRD 的假设 | 本项目**已拍板** | 判定 |
|---|---|---|---|
| 机构形态 | 集团/机构 → 校区（`Organization` / `Campus` 两个实体；登录后**选择校区**；角色含"集团/机构管理员""校区负责人"） | **单校区自用**，不为多校区预留架构（ADR-001） | ❌ **冲突** |
| 使用人群 | 8 个内部角色 + **家长端 + 学生端** | admin / teacher **两角色**；学员家长**无账号、不登录**（ADR-002、v14 已删除家长账号） | ❌ **冲突** |
| 学员规模 | 未写（按实体设计推是集团级） | **200–500 学员 / 5–15 员工** | ❌ 不适用 |
| 触达 | 「上课提醒 → **向家长/学生发送**」「消息中心」 | **不做任何出网触达**（短信/微信/推送全不做，ADR-002） | ❌ **冲突** |
| 教学范围 | 含**作业中心**（布置/提交/批改/统计） | 「作业布置与提交批改」明确 Non-goal | ❌ 冲突 |
| 权限 | RBAC + 数据范围 + 分级授权 + **数据管理员角色** | 两角色 + 四层权限；「自定义角色权限」是 Non-goal | ⚠ 模型可借、角色不可借 |
| 技术假设 | 数据仓库 / ETL / 数据血缘 / API 版本化 / OAuth / 向量库（"AI 平台可以拥有自己的特征库、向量库"） | 单机 **SQLite + Express**，单校区 Docker；**系统是唯一数据源也是唯一仓库**（ADR-008，且**不自建向量库**） | ❌ 过度设计 |
| 定位 | 「AI 平台的**上游数据底座**」 | 教务系统是业务系统；数据资产化是 Phase 6（**未排期**，且"不得早于 Phase 1–4"） | ⚠ 方向一致、次序不同 |

**读法**：凡是被标 ❌ 的，**它的功能设计一律不能照搬**（比如"选择校区""家长端授权与撤回""按家长推送"）。
但它的**建模思想**（怎么设计主键、怎么留痕、怎么定义口径）与产品形态无关，这才是可借的部分。

## 2. ★ 强印证：两个独立来源指向同一结论

> 这是本次分析最有决策价值的部分。昨天我基于本项目 schema 独立得出 4 处结构性缺口；
> 这份 PRD 在**完全不知道本项目**的情况下，独立给出了相同方向的建议。

| 我昨天的判断（S1–S4） | 这份 PRD 的主张 | 印证强度 |
|---|---|---|
| **S1** 没有「课次实例」实体（`schedules` 只是周模板，考勤/课评/补课全靠日期字符串近似） | §6.4「**每一节课生成唯一 `lesson_instance_id`，作为签到、课消、作业、课堂记录等数据的连接键**」；§6.5「补课**必须关联原始缺课课次**」「调课**必须建立前后课次关联**」；§20 **决策2**：每节真实发生的课次必须有唯一 ID，作为教学事件枢纽 | ★★★ **完全一致** |
| **S2** 教师只有「班主任」维度，任课老师看不到自己的班 | §3 角色表明确列「**任课教师** — 备课、上课、签到、课… — **本人授课班级/学生**」 | ★★★ 一致（且说明"任课维度"是行业标配） |
| **S3** 学员状态口径分叉（`students.status` 在读/休学/退学 vs `orders.status` 在读/结业/退班，且 `students` 没有"结业"） | §5.1 给出**完整生命周期状态机**：潜在线索 → 试听中 → 在读 → 暂停 → 毕业/结业 → 流失/终止 → 归档，**每个状态标注允许操作** | ★★★ 直接可用作统一方案 |
| **S4** 没有指标口径字典，指标散在各路由 SQL 里 | §8.1 数据质量规则含「**口径统一** — 出勤率、课消率、续费率… — **指标字典管理**」；§20 **决策5**「所有核心字段必须有明确口径与数据字典」 | ★★★ 一致 |
| （我另提的）**成绩修改留痕与审批** | §8.2 数据修正机制：「必须保留**原值—新值—原因—操作者—审批人—时间—来源**，**禁止直接覆盖后无痕**」 | ★★★ 一致，且给了完整字段清单 |

> ★ **结论**：这 5 条**不再是我的个人判断，而是两个独立分析给出同一结论**。
> 建议：**直接提升到 P0，并各写一个 ADR 把口径定死**（它们都会改变现有表结构语义）。

**顺带印证的另一条**：我在报告里提醒「本报告未验证校区老师真实使用反馈」——这份 PRD 在 §21 也把「机构实际使用的成绩/评价体系和课程知识点体系」列为**开发前必须确认**项。同一条风险被两处提到。

## 3. 模块覆盖对照：我们真正"整块空缺"的只有一个

> PRD §4 信息架构给了 13 个一级模块。逐一对到我们的页面：

| PRD 一级模块 | 本项目对应 | 状态 |
|---|---|---|
| 工作台 | `welcome/index.vue` + 铃铛待办 | ✅ 已有 |
| 学生中心 | `attendance/students` | ⚠ **薄**（无监护关系表、无附件、无标签、无操作时间线） |
| 课程中心 | `attendance/courses` | ⚠ **薄**（单层：code/name/teacher，无学科/课程体系/阶段分层） |
| 班级中心 | `attendance/classes` | ⚠ 薄（无班型、无容量、无教室） |
| 排课中心 | `schedules` + `adjustments` + `makeups` + `terms` | ✅ 较完整（**缺课次实体**） |
| 考勤中心 | `checkin` / `records` / `leaves` / `statistics` | ✅ **最强项** |
| 教学中心 | `teaching/*` + `class_evaluations`(v18 表已建) | ⚠ 部分 |
| 考试中心 | `teaching/exams`（`exams` / `exam_scores`） | ⚠ 薄（成绩是单一扁平分数） |
| 学员服务 | `family/notifications` | ⚠ **薄**（只有单向"已发送通知存档"，无双向沟通记录） |
| 收费中心 | `finance/*`（6 页） | ✅ 已有 |
| 招生转化 | `recruit/leads` | ⚠ 部分（**试听/体验课缺**，F8 已认领） |
| 报表中心 | `analytics` + 各模块统计 | ⚠ 部分（12 指标 + 分模块统计，缺经营漏斗一页） |
| **数据中心** | **无** | ❌ **整块空缺** |
| 系统设置 | `system/*`（含员工/公告/备份/审计/设置） | ✅ 已有 |

> ★ **这张表回答了"哪些值得借鉴"最核心的一问**：
> **我们缺的不是"十几个模块"，而是"一个层"** —— 数据中心（数据字典 / 指标口径 / 数据质量规则 / 对外数据服务契约）。
> 其余 12 个模块我们都有，只是**深浅不同**：**最薄的三个是「学生中心」「学员服务」「考试中心」**。

## 4. A 类 · ★ 高价值，可直接采纳（8 项）

> 判定标准：**与产品形态（单/多校区、有无家长端）无关**，且对本项目 200–500 学员规模**不过度**。

| # | 借鉴项 | 作用 | 对本项目的具体落点 | 对应我报告 |
|---|---|---|---|---|
| **A1** | **课次实例 `lesson_instance_id`** | 把"每周三第 3 节"变成"2026-09-23 第 3 节 · 张老师 · 302 教室 · 已上/停课/调课"；成为签到/课消/课堂记录/课评的**统一连接键** | 新建 `class_sessions`；`attendances` / `hour_consumptions` / `class_evaluations` / `makeup_classes` 增加 `session_id` | **S1** |
| **A2** | **学生生命周期状态机** | 用一个状态机取代两处互相打架的状态字段 | 合并 `students.status` 与 `orders.status` 的口径；补 PRD §5.1 缺的"结业""流失""归档"三态 | **S3** |
| **A3** | **数据修正留痕（原值—新值—原因—操作者—审批人—时间—来源）** | 谁把 60 改成 90 必须可追 | 先覆盖**成绩**（最对外敏感），再扩到缴费/退费；`exam_scores` 现在**没有 `updated_at`，连"被改过"都不知道** | 成绩留痕 |
| **A4** | **指标口径字典** | 同一指标多处 SQL 会算出不同数字 | 抽一个 `metrics` 常量模块 + 一份《指标口径字典》md；每个指标写清**定义/公式/排除项/数据源表** | **S4** |
| **A5** | **事件模型补强**（`schema_version` / `trace_id` / **幂等**） | 我们的 `student_timeline`（v18）已实现"只增不改 + event_type + payload"，**思路已被验证是对的**；PRD 补了 3 个我们缺的字段 | ① `payload` 加版本号（将来改结构不用洗历史）② 加 `trace_id`（一次业务操作产生的多条事件可串起来）③ **相同 event_id 重复推送不产生重复事件**（对应我们的幂等诉求） | — |
| **A6** | **「考勤状态 × 课消影响」规则矩阵** | 把"请假扣不扣课时""旷课全扣吗"从代码逻辑变成**可配置的矩阵** | 照 PRD §6.5 的表格做成配置页：每行一个考勤状态（正常/迟到/早退/请假/缺勤/补课/调课），列"是否计课时消耗""消耗比例""备注"。**这是最容易产生家长争议的规则** | 课时扣减规则可配 |
| **A7** | **课消必须挂到课次** | 收入确认与家长对账的唯一依据 | 我们 `hour_consumptions` 现在只有 `date` + `class_id` + `course_id`（**没挂课次**）。挂上课次后，"这一节课到底扣了谁的多少课时"才可精确对账 | 与 B4 收入确认口径相关 |
| **A8** | **课程体系分层**（学科 → 课程体系 → 课程 → 阶段/模块 → 课次 → 知识点） | 续报推荐、知识点归属、教学一致性都需要中间层 | 我们 `courses` 是单层。建议至少补「**学科**」与「**课程体系/阶段**」两层的轻量实现（可先用字典字段，不必立刻建表） | 课程进阶路径 |

## 5. B 类 · ⚠ 值得借鉴，但**必须改造**（11 项）

> 判定标准：**思路对，但直接照搬会与本项目规模 / 边界冲突**，需要按本项目重写。

| # | 借鉴项 | PRD 原样 | 本项目改造后 |
|---|---|---|---|
| **B1** | **任课教师维度** | 8 个角色 + RBAC + 数据范围 | **只借"任课教师"这一个维度**（解 S2），**不加角色**。做成 `teaching_assignments(class_id, course_id, teacher_id)`，归属过滤改为「班主任 **OR** 任课教师」 |
| **B2** | **班型** | 固定班 / 走班 / 1对1 / 1对多 / 短期集训 / 专题课 | **借"班型"字段**（影响容量、课时规则、排课），但**不做走班**（单校区 200–500 学员无走班场景） |
| **B3** | **监护关系** | `Guardian` 独立实体 + 授权关系 + 家长端账号 | **只做档案侧**：多监护人 + 监护类型（父/母/祖辈/其他）+ 紧急接送人。**不建账号、不做授权撤回**（ADR-002） |
| **B4** | **沟通记录** | 沟通绑定 `student_id`，类型标准化（学习反馈/请假/续费/投诉/活动/阶段回访），**原文 + 结构化标签**（满意/一般/需跟进） | **只做内部服务记录**：把 `family/notifications` 从"已发送通知存档"扩成"**沟通/回访记录**"（谁在何时跟哪位家长聊了什么、结论是什么）。**不做家长端消息中心** |
| **B5** | **学生档案结构** | 基本档案 / 监护关系 / 学段经历 / 学习经历 / 标签 / 服务记录 / 附件 / 操作时间线（8 个页签） | **借这个页签结构**。我们 `students` 缺：**出生日期、年级（现在只有 `classes.grade`）、监护关系表、附件、标签、操作时间线**（`student_timeline` 已有，可复用为"操作时间线"） |
| **B6** | **考试类型扩展** | 机构自测 / 阶段测评 / 月考 / 期中 / 期末 / 专题测验 / 诊断测评 | 我们 `exams.type` 的 CHECK **只有 `单元测` / `期中` / `期末`** → 扩枚举即可（**注意：SQLite 改 CHECK 需重建表，要走迁移**） |
| **B7** | **成绩分层** | 考试 → 科目 → 题目 → 知识点 → 能力（理解/应用/迁移）→ 答题过程 | **只取"知识点"这一层**（对齐既有 D7 的"知识点体系最小集"）。**科目**可用 `course_id` 隐含；**题目级/能力级/答题过程**超出边界（题库是 Non-goal） |
| **B8** | **报表域划分** | 招生 / 教务 / 教学 / 学员 / 课程 / 服务 / 财务（7 域） | **直接借这个分域**作为报表中心的信息架构，比我上一份报告的"经营漏斗一页"更有组织性 |
| **B9** | **数据质量规则** | 唯一性 / 完整性 / 一致性 / 时序性 / 引用完整 / 口径统一（6 类）+ 异常队列 | **借规则清单 + "异常队列"这个机制**（质量问题不阻断保存，但进队列待处理）。我们的具体落点：**重复学员检测**、必填校验、引用完整（对应 H5 逻辑删除未过滤） |
| **B10** | **软删除 / 状态化** | 「删除/归档不得破坏历史引用」 | 对应我们的 **H5（逻辑删除未过滤）+ Later 的"回收站与软删除"**。PRD 的表述可用来固化口径：**历史可查优先于物理删除** |
| **B11** | **非功能需求基线** | 性能 / 可用性 / 可扩展性 / 可维护性 / 审计 / 安全 / 数据一致性（幂等）/ 接口（版本化·鉴权·限流） | **借这张"检查表"**作为我们 Gate 3 的补充清单（我们已有 helm/限流/审计，缺**幂等**与**接口版本化**的明确约定） |

## 6. C 类 · ❌ 明确不采纳（7 类）

> 不是"它不好"，而是**与本项目已拍板边界冲突，或对 200–500 学员规模属过度设计**。

| # | 不采纳项 | 冲突依据 |
|---|---|---|
| **C1** | **多校区 / `Organization` / `Campus` / 登录后选择校区 / 集团-校区两级** | **ADR-001**：单校区自用，砍掉多校区、租户隔离、跨校区汇总，**不为这些预留架构**。ROADMAP R6 明确"不预留" |
| **C2** | **家长端 + 学生端**（我的孩子 / 课程表 / 学习记录 / 消息中心 / 订单课时 / 授权隐私） | **ADR-002**：不做家长端，不做家长账号体系与家校绑定（**v14 已删除，声明"不回摆"**） |
| **C3** | **任何出网触达**（"上课提醒 → 向家长/学生发送提醒"、作业逾期提醒学生） | **ADR-002**；ROADMAP 强调"不做任何出网触达"，且**不建议留适配层**（过度设计） |
| **C4** | **作业中心**（布置 / 提交 / 批改 / 得分 / 统计 / 作业逾期提醒） | ROADMAP Non-goals：「作业布置与提交批改」明确排除 |
| **C5** | **8 角色 RBAC + 自定义角色 + 分级授权 + 数据管理员** | Non-goals：「自定义字段、自定义角色权限（admin/teacher 两角色够用）」。**对 5–15 人机构，角色膨胀是负资产**（维护成本 ↑、配置易错）。若确有需要，最多加 **1 个「前台/教务」只读角色** |
| **C6** | **数据分层（L1–L4）/ ETL / 数据仓库 / 数据血缘 / 向量库 / OAuth / API 版本化平台** | ① 规模不符：500 学员单机 SQLite 上数仓是纯浪费；② **ADR-008** 已定"系统是唯一数据源**也是唯一仓库**"，AI 是加工厂（只读）；③ 有**过度设计审计**先例（2026-09-14 净减约 1000 行 / 5 依赖） |
| **C7** | **"覆盖小学至高中毕业的全生命周期底座"**（跨学段统一档案、学段升级、年级变更、升学关系迁移） | 培训机构学员会升学，但"**建立一个跨三学段的学生数据底座**"是**学历教育视角的产品野心**，不适合单校区培训机构。可借鉴的只有一句："**不因升年级而丢历史**"——我们已满足（学员档案与历史数据不随班级变更丢失） |

> ★ **一句提醒**：C1/C2/C3/C5 若被"照 PRD 补齐"，会直接推翻 4 条 ADR。
> 建议在 ROADMAP Non-goals 处**强化重申一次**，防止将来有人拿这份 PRD 来要求加"家长端/多校区"。

## 7. 这份 PRD 自身的产品级缺陷（评审意见）

> 用户是拿它来"借鉴功能"的，所以有必要先说清**它哪里不能信**。

| # | 缺陷 | 说明 | 严重性 |
|---|---|---|---|
| 1 | **决策顺序颠倒（最严重）** | 决定整个架构的前提——"单校区还是多校区""家长端形态"——被放在 **§21「后续进入原型与技术设计前，必须进一步确认的事项」**。而 **§7.2 的数据模型早已按多校区画好**（`Organization` + `Campus` 两个实体）。**先画模型、后问边界 = 一旦确认单校区，整个 §7 要重画** | 高 |
| 2 | **没有可量化的成功指标** | §2.1 目标全是定性（"建立一套…""实现…线上化"），**无北极星、无 KPI、无验收数值**。一份"产品需求文档"缺这一章，就无法判断它是否成功 | 高 |
| 3 | **"建议"多于"要求"，无法开发** | 通篇"建议从项目第一天就…""推荐架构…""可以考虑…"。需求条目（如 WD-001~004）只有 4 条，其余全是**规划性描述**。**这是数据资产规划，不是可开发的需求规格** | 高 |
| 4 | **数据模型不可执行** | §7.2 列了 23 个实体名 + "与谁关联"，但**无字段级定义、无枚举字典、无 ER 图、无基数（1:N / N:N）**。照着它没法建表 | 中 |
| 5 | **验收标准不可执行** | §19 写成"随机抽取学生，从首次…""任意一节课都能追溯到…"（句子本身还是截断的），**没有可判定的通过/失败条件** | 中 |
| 6 | **角色膨胀与规模不匹配** | 8 个内部角色 + 家长端 + 学生端，对 200–500 学员 / 5–15 员工机构是**结构性问题**（真实场景：一个人干 3 个角色） | 中 |

**它做得好的地方（值得学）**：
- **§13 隐私与合规基线 + §23 引用 3 部法规**（个保法未成年人条款 / 网络数据安全管理条例 / 儿童个人信息网络保护规定）——**最专业的一章**。我们目前**没有任何专门章节**。
- **§8.2 数据修正机制**（原值—新值—原因—操作者—审批人—时间）——一条就能拿去用。
- **§20 产品设计决策记录（8 条"必须坚持"）**——这个形式很好，与我们 ADR 制度同源。
- **§7.3 事件模型**的字段设计——与我们的 `student_timeline` 思路一致，可互补。
