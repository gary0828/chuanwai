## 一、结论先行

你感觉"很乱"，但**扫描结果和直觉不一样**：

| 你的担心 | 实际情况 |
|---|---|
| 「做了很多重复功能」 | ❌ **全系统只有 2 处真重复**，且都不在菜单上、老师感知不到 |
| 「菜单太乱」 | ✅ **这个判断是对的** —— 8 个一级分组里，**有 4 个是"什么都往里塞"的筐** |

所以真正要动的不是"删重复功能"，而是**重新分层菜单** + 顺手清掉 2 处技术负债。

## 二、两处「真重复」（有证据）

### 🔴 重复 1：数据库备份有两套独立实现

| | 应用内（页面） | 运维脚本 |
|---|---|---|
| 入口 | 系统管理 → 数据备份 | SSH 跑 `server/scripts/backup-db.sh` |
| 实现 | `fs.copyFileSync` + `wal_checkpoint(TRUNCATE)` | `VACUUM INTO`（单读事务快照） |
| 证据 | `server/src/utils/backup.js:23-46` | `server/scripts/backup-db.sh:33-47` |
| 产物 | `server/data/backups/backup-*.db` | `server/data/attendance-*.db` |
| 保留 | 自动 20 份 | 无（人工） |
| 恢复 | 页面按钮 → 覆盖主库 → 退出进程 | `restore-db.sh` |

**问题**：两者都指向同一个 SQLite 主库，**目标完全一致**。而且**技术路线不同**——
`backup-db.sh:5-8` 的注释明确批评过 `cp` 方案会漏掉 `-wal` 未落页、可能拷出损坏副本，
而应用内的 `backup.js` **正是它批评的那种做法**。

**结论：两套都保留，但让应用内改用 `VACUUM INTO`** —— 统一成一份安全实现。
理由：
- 应用内不能删：它是**唯一**让校区管理员自助备份/恢复的通道（运维脚本要登服务器 + 会 Docker）
- 脚本不能删：它是停机外的独立兜底，灾难恢复靠它
- **但两套用不同技术写同一件事 = 未来口径漂移**，必须统一

### 🟠 重复 2：出勤率有两套算法，数字对不上

| | `attendance.js`（统计报表用） | `analytics.js`（AI 数据出口用） |
|---|---|---|
| 公式 | `(总数 - 缺勤) / 总数` | `实到 / (总数 - 请假)` |
| 请假怎么算 | **计入分母**（算作"应到但没来"） | **不计入分母**（请假不算缺勤） |
| 证据 | `server/src/routes/attendance.js:732` | `server/src/routes/analytics.js:230,309` |

**同一个指标"出勤率"，两个页面给两个答案。** 举例：100 条考勤里 10 条请假、5 条缺勤

- attendance.js：`(100-5)/100 = 95%`
- analytics.js：`85/(100-10) = 94.4%`

**结论：必须统一。** 建议以 **`attendance.js` 的口径为准**（请假计入分母），并把公式抽成公共函数。
理由：请假是否该算"缺课"，业务上通常算（占用了课时安排）；且这个口径**老师已经在看了**，改动影响面小。

> ⚠️ 注意：`analytics.js` 目前**没有任何前端调用**（`src/api/` 里无 `analytics.ts`，全仓搜 `analytics` 零命中），
> 是个**孤儿接口**。所以这个不一致**目前还没被用户看见**——但 AI 分析功能一旦上线就会暴露。
> 建议：保留它（它是唯一的结构化 CSV 导出通道，且是为 AI 预留的），**但先把公式统一**。

## 三、差点被误判为"重复"的（扫描后确认**不重复**）

这几组**长得像重复，实际是合理分层**，请不要动：

| 组 | 为什么看着像重复 | 实际为什么不是 |
|---|---|---|
| 排课模板 vs 周课表 | 两个都是"课表"，都是星期网格 | **模板 vs 实例**：一个改"以后每周都变"，一个改"就这一节"。改不同表（`schedules` / `class_sessions`），已有消歧文案 `schedules/index.vue:242` |
| 调课审批 vs 课次挪课 | 都叫"调课" | 两个维度：改长期模板 vs 挪单节课。**工作区未提交改动已把后者改名"挪课"**，方向正确 |
| 考勤登记 vs 考勤记录 | 两个都能改考勤 | 登记=批量录入（`checkin`），记录=查询订正导出（`records`）。属**互补**，不是重复 |
| 学习报告 vs 成长档案 | 都是"选学员→展示"，选择器代码几乎一样 | 报告=**当前状态切片**，档案=**历史事件流**。可考虑合并成一页两 tab（见 §5 建议） |
| 员工账号 vs 个人中心 | 都能"改密码" | 改**别人**（管理员重置，不需原密码）vs 改**自己**（需原密码 + 强制重登）。标准自助/后台双入口 |
| 经营报表 vs 财务统计 | 都算营收 | 看板 vs 工具：经营报表含**续班率/线索转化**，财务统计可筛选查欠费明细。**只有"近12月营收"指标重叠** |
| 待办 / 公告 / 家校通知 | 三个都叫"通知" | 三种不同事物：个人任务 / 管理员公告 / 系统自动家校通知。**三张独立表**。历史"消息"tab 已主动砍掉（`lay-notice/index.vue:14-16` 有注释） |
| 系统参数 vs AI 配置中心 | 都能"配置" | **表层面刻意隔离**：`settings` vs `ai_settings`（`017-ai-settings.js:9` 注释）。无交集 |
| 课程"授课教师" vs 任课关系 | 都叫"授课教师" | 文本字段（展示）vs 外键关系（权限依据）。**但过渡期双读有隐患**，见 §4 |
| 学期 / 节次时间 / 排课模板 | 三个都定义"什么时候上课" | 三个**正交维度**：学期范围 × 第几节几点 × 周几第几节 |
| 成绩管理 vs 报告里的成绩 | 都出现"成绩" | 成绩管理是**唯一写入口**，报告/档案是只读视图 |
| AI 工作台待办 vs 教务端待办 | 两端都有待办 | **刻意共用同一张表**按角色过滤（用户 09-21 拍板），不是两套 |

## 四、⚠️ 一个隐患（不是重复，但会咬人）

**`courses.teacher`（文本）与 `teaching_assignments`（外键）双数据源并存**

- 课程管理页的"授课教师"是**自由文本**，与班级无关（`courses.teacher`，`database.md:108-116`）
- 任课关系页是**班级×课程×教师×学期**四元关系，是"老师能看到自己班"的**权限依据**（`teaching_assignments`）
- 冲突检测**同时读两处**（`server/src/routes/schedules.js:39-84`，双路并存取并集）
- 课次生成**只读任课关系**（`session-engine.js:64-84` 的 `resolveTeacher`）

**风险**：若两者不一致 → 课程页显示"张老师"，但课次和权限实际按"李老师"算。**管理员改了课程页的教师却什么都没发生。**

**建议**：
1. 课程页那个输入框**改标题为「默认授课教师（仅供展示）」**，并加说明"实际任课请在【任课关系】里设置"
2. 暂**不删** `schedules.js:67-83` 的兜底分支（历史数据未确认迁完，删了可能漏检冲突）
3. 等确认历史数据全部迁入任课关系后，再删兜底分支

## 七、菜单重构方案（**待你拍板**）

### 设计原则

1. **按"老师每天要干什么"分组**，不按"数据表怎么设计"分组
2. 一级分组控制在 **6–7 个**（超过 7 个，人就要开始找）
3. 每个分组的子项控制在 **≤6 项**
4. **配置类**（不常改的）与**日常操作类**分开
5. 高频入口保持**浅**（1 次点击到达）

### 方案 A · 按业务流程重组（**推荐**）

```
📋 待办                          ← 不变（rank 0，第一入口）
🏠 首页

── 日常教务 ──────────────────────────────
📊 考勤管理
   ├ 考勤登记          ← 老师每天用
   ├ 考勤记录
   ├ 请假管理
   └ 统计报表

🗓 排课与课表          ← 从"考勤管理"+"数据管理"抽出，归为一处
   ├ 排课模板
   ├ 周课表
   ├ 调课审批 🔒
   ├ 补课管理
   ├ 节次时间 🔒
   └ 任课关系 🔒

── 学员与教学 ────────────────────────────
👥 学员管理            ← "班级/学生/课程"从"数据管理"抽出
   ├ 学生管理
   ├ 班级管理
   ├ 课程管理 🔒
   └ 学期管理 🔒

📖 教学成果            ← 原"教学结果"改名
   ├ 成绩管理
   ├ 学习报告
   └ 成长档案

── 招生与财务 ────────────────────────────
🎯 招生与报名          ← "线索管理"+"报班管理"合并（前后衔接的同一件事）
   ├ 线索管理
   └ 报班管理

💰 财务                ← 原"财务管理"
   ├ 缴费记录
   ├ 退费管理
   ├ 课消统计
   ├ 财务统计 🔒
   └ 经营报表 🔒

── 家校与系统 ────────────────────────────
💬 家校沟通
   └ 通知记录

⚙️ 系统管理 🔒
   ├ 员工账号
   ├ 系统参数
   ├ 通知公告
   ├ 数据备份
   └ 审计日志
```

**变化点**：
- **考勤管理 8 项 → 4 项**（课表体系搬走）
- **数据管理 7 项 → 拆解消失**（学员档案进"学员管理"，排课配置进"排课与课表"，教务流程进"排课与课表"）
- **招生管理 + 报班管理 → 合并为"招生与报名"**（线索转化后就是报班，同一业务链）
- **员工账号**从独立项移入"系统管理"（和它同类）
- 一级分组 **8 → 7 个**（含独立项）

### 方案 B · 保守方案（改动最小）

只做**两件事**，不动分组结构：
1. **把课表体系从"考勤管理"搬到"数据管理"**（因为"数据管理"里已有排课模板，同类归拢）
2. **"数据管理"改名"基础数据"**，消除"什么都装"的观感

**适合**：你担心老师已经记住位置了，不想大动。

### 方案对比

| | 方案 A（推荐） | 方案 B（保守） |
|---|---|---|
| 老师需要重新适应 | 中等（分组名变了，但更好找） | 低（只挪 4 项） |
| 解决"乱"的程度 | ✅ 彻底 | ⚠️ 缓解 |
| 改动文件 | `server/src/routes/auth.js` 的 `ROUTES`（1 处） | 同左（改动更小） |
| 风险 | 老师可能找不到熟悉的功能（需通知） | 低 |

## 八、风险与不改的东西

**本方案不动**（明确说明，避免误伤）：
- ❌ 不删任何功能页面 —— 扫描确认绝大多数是合理分层
- ❌ 不动数据库表结构（除 §4 的展示层标注）
- ❌ 不动权限体系（原因：§5 那条 `consumption` 矛盾经核实是**误报**，权限本来就是对的，见 §5 说明）
- ❌ 不动 AI 工作台

**改菜单的实际影响面**：只改后端 `ROUTES` 常量（`server/src/routes/auth.js:22-260`），
前端动态菜单自动跟随（pure-admin 的 `getAsyncRoutes` 消费同一份数据）。
**`rank` 字段决定排序**，新分组要重新编号。

**要注意的坑**：菜单路径（`path`）**不能改**，因为它是路由地址，老师可能收藏了页面。
只改 `meta.title` 和分组结构（`children` 归属）。
