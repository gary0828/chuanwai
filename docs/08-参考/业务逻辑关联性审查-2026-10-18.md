## 四、多写入源矩阵（关联性的结构性风险）

统计口径：某表被几个路由文件执行 `INSERT/UPDATE/DELETE`。

| 表                  | 写入方                                                              | 说明                                                              |
| ------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------- |
| **`orders`**        | **6**：`attendance` `finance` `leads` `leaves` `makeups` `students` | 其中 `remain_hours`（课时余额）被 5 处直接 UPDATE，**无单一入口** |
| `hour_consumptions` | 4：`attendance` `finance` `leaves` `makeups`                        | 流水写入同样分散                                                  |
| `notifications`     | 4：`attendance` `exams` `leaves` `notifications`                    | 通知文案各自拼接，无模板集中                                      |
| `attendances`       | 2：`attendance` `leaves`                                            | 请假审批反写考勤状态（有幂等保护）                                |
| `leaves`            | 2：`attendance` `leaves`                                            | 考勤"请假"自动生成同步单，属设计内                                |
| `schedules`         | 2：`adjustments` `schedules`                                        | 调课审核后改排课                                                  |

**结论**：`orders.remain_hours` 是全项目最热的数据点。已有 `utils/hours-reconcile.js` 做对账兜底（幂等，可反复跑），所以当前不会累积漂移；但**任何一次口径调整（如"1 节 = 2 课时"）仍需同步改 5 处**，这是本次审查发现的最大维护风险。

## 五、问题清单

### P0-1 删除班级漏检 6 类关联数据，课次/任课/评价被静默删除

- **位置**：`server/src/routes/classes.js:174-185`
- **现象**：删除前的关联检查写死 6 张表（`students` + `schedules` `exams` `schedule_adjustments` `makeup_classes` `hour_consumptions`），查完即 `DELETE FROM classes`。
- **证据**：数据库实际外键显示 `classes` 被 **12 张**表引用：

```
students(RESTRICT)  orders(SET NULL)  exams(CASCADE)  hour_consumptions(CASCADE)
makeup_classes(CASCADE)  student_timeline(SET NULL)  kp_assessments(SET NULL)
teaching_assignments(CASCADE)  class_evaluations(CASCADE)  class_sessions(CASCADE)
schedules(CASCADE)  schedule_adjustments(CASCADE)
```

- **漏检的 6 张**：`class_sessions`(CASCADE)、`teaching_assignments`(CASCADE)、`class_evaluations`(CASCADE)、`orders`(SET NULL)、`student_timeline`(SET NULL)、`kp_assessments`(SET NULL)。
- **触发条件**：班级下学生已全部转走、但学期课次已生成（排课不依赖学生，这是常态）→ 删除班级成功、返回 `success:true`，**课次连同其考勤锚点、课堂评价、任课关系一起消失，无任何提示**。`orders.class_id` 被置空后，财务的班级归属统计随之失真。
- **同项目内的对照**：`courses.js:97` 已改用 `scanReferences("courses", id)` 自动发现引用（K-052 修复），`classes.js` 未跟进 —— **同一类缺陷修了一处、漏了另一处**。
- **建议**：`classes.js` 改接 `utils/delete-guard.js` 的 `scanReferences` + `describeImpacts`，与 `courses` `rooms` `terms` `orders` 保持同一实现。

### P0-2 删除学员的影响面清单少算 3 类数据，确认框数字失真

- **位置**：`server/src/routes/students.js:580-597`（`buildDeleteImpact`）、`:605`（`GET /:id/delete-impact`）
- **现象**：清单写死 6 张表：`attendances` `leaves` `makeup_classes` `hour_consumptions` `notifications` `exam_scores`。
- **证据**：`students` 实际被 **13 张**表引用，其中 `orders` `payments` `refunds` 为 RESTRICT（已有前置拦截，`students.js:641`，正确）；**漏列的 CASCADE 三张**：`class_evaluations`、`kp_assessments`、`student_timeline`。
- **后果**：`/delete-impact` 与删除响应里的 `cascade` 计数**都少 3 类**。用户在确认框看到"将删除 12 条考勤、3 条请假"，实际还会静默删掉课堂评价、知识点测评、成长档案 —— 正是 **K-050「静默即缺陷」** 的形态。
- **建议**：同样改接 `scanReferences("students", id)`，并把 RESTRICT 表显式标为「阻止删除」而非「将删除」。

### P1-1 课时扣减的「单一权威」收口只完成一半

- **位置**：`server/src/utils/hours-reconcile.js:1-30`（文件头注释）vs 实际代码
- **现象**：注释明确写「`attendance.js` / `makeups.js` / `leaves.js` 原先各自复制了一份代码（三处重复，改一处必漏两处）。本次统一收口到本文件：三个调用方只负责"什么时候对账"，**不再自己写 SQL**」。
- **证据**：只有 `attendance.js:14` 真正 `require("../utils/hours-reconcile")` 的 `reconcile`；`leaves.js:8` 与 `makeups.js:9` **只 import 了 `SOURCE` 常量**，扣减仍是自带 SQL：

```
leaves.js:153   UPDATE orders SET remain_hours = MIN(total_hours, remain_hours + 1) ...
makeups.js:124  UPDATE orders SET remain_hours = MAX(0, remain_hours - 1) ...
makeups.js:127  UPDATE orders SET remain_hours = MIN(total_hours, remain_hours + 1) ...
makeups.js:179  UPDATE orders SET remain_hours = MIN(total_hours, remain_hours + 1) ...
```

- **影响**：不是当前 bug（三处逻辑目前等价），但**注释与代码漂移会误导下一个人**：改动口径时按注释以为只需改一处。
- **建议**：二选一 —— ① 把回补/补课扣减也收进 `hours-reconcile`；② 在注释里如实说明"回补路径仍各自实现，原因是 X"，并在三处加交叉引用注释。

### P1-2 19 个删除端点中只有 4 个接入统一守卫

| 已接 `scanReferences`                              | 未接（硬编码或裸删）                                                                                                                                                                                                         |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `courses` ✓ `rooms` ✓ `terms` ✓ `finance/orders` ✓ | `classes` `students` `users` `exams` `leads` `makeups` `schedules` `adjustments` `teaching-assignments` `period-times` `notices` `todos` `qbank/questions` `qbank/taxonomy/*` `finance/payments` `finance/refunds` `backups` |

- **需要区分的**：`backups`（删文件）、`todos`、`notices`、`period-times` 等表引用面小，裸删可接受；**真正需要补的是 `classes`（P0-1）与 `students`（P0-2）**，以及 `exams`（`exam_scores` 为 CASCADE，当前注释已明示"成绩由外键级联删除"，属有意为之，但应在响应里回报删除条数）。

### P1-3 学员转班会批量改写历史订单的班级归属

- **位置**：`server/src/routes/students.js:559`
- **代码**：`UPDATE orders SET class_id = ? WHERE student_id = ? AND status = '在读'`
- **现象**：转班时把该学员**全部在读订单**的 `class_id` 改成新班级。
- **判断**：从业务看合理（订单跟随学员）。但 `orders.class_id` 同时被财务的「班级维度课消/收入」使用（`finance.js:905-946`），**历史期间的班级业绩会被追认为新班级**。是否可接受 → 需拍板（见第七节）。
- **目前状态**：无缺陷证据，仅口径疑问。列此是为了避免下轮重复讨论。

### P2-1 两个「收入」口径并存

## 六、已验证正确（下轮不必重复审）

以下几项**查过、确认没问题**，写在这里是为了压缩下一轮的审查成本：

1. **前后端接口零断链**：209 条后端路由 vs 144 条去重调用，全部匹配。初判的 5 条"断链"均为脚本漏抓跨行定义（`router.get(\n "/:id/scorecard"`）导致的假阳性。
2. **教师权限链路自洽**：teacher 可见 15 个页面；后端 79 条 `requireRole("admin")` 独占接口中，10 处能被教师页面经 API 层触达，逐条核对后**前端均有 `isAdmin` 守卫**：
   - `classes/index.vue:53` `if (!isAdmin.value) return;`
   - `sessions/index.vue:97` `if (isAdmin) { ... getUserList ... }`
   - `SessionDetailDrawer.vue:559` `<template v-if="isAdmin && session" #footer>`
     → 无「前端能点、后端 403」的断链。
3. **课次生成幂等**：`session-engine.js:332` `ON CONFLICT(class_id, session_date, period) DO NOTHING`，重复生成只累加 `skipped`。
4. **考勤扣课有对账兜底**：`attendance.js:335-357` 提交后调用 `reconcile()`，补扣漏扣（订单无课时包 / 先点名后报班 / 退班后改回在读三种历史事故场景已覆盖）。
5. **请假审批回补条件正确**：`leaves.js:186-201` 只对 `状态 IN ('正常','迟到','早退')` 的考勤回补 —— 这三种才是已扣过课时的状态；「请假」「缺勤」不回补，不会凭空加课时。
6. **课时余额上限有保护**：所有回补都用 `MIN(total_hours, remain_hours + 1)`，不会超过总课时。
7. **收入净额已退费**：`finance.js` 的实收与欠费均改用净额（ADR-003），退出来的钱在报表里可见。
8. **`orders` 删除有守卫**：`finance.js:365` 用 `scanReferences`，且显式拦 `hour_consumptions`（CASCADE 历史遗留）。

## 七、待用户拍板

1. **课时单位**：现状「1 节课 = 1 课时」硬编码在 6 处。`hour_consumptions.hours` 字段保留且历史数据有 `2`（老口径）。是否需要支持"一节课按多课时扣"？若不需要，建议在 `attendance-rules.js` 里把 1 定义成常量并全项目引用，堵住"改口径改漏"。
2. **删除策略**：学员档案是否改为软删（`status = '已删除'`）？现在硬删会级联清空考勤、评价、成长档案 —— 教务数据通常需要留档。
3. **转班是否改写历史订单班级**（P1-3）：影响历史班级业绩，属业务决策。
4. **P0-1 / P0-2 的修法**：改接 `delete-guard` 会让若干"以前能删"的班级/学员变成"不能删"，需要确认这是期望行为（我判断是，但会改变现有可见行为）。
