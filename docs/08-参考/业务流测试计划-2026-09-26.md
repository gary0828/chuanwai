# 业务流测试计划（Usage-First）

> **为什么做这个**：用户反馈「批量上传学生信息时没有任何反应」。
> 一查发现 —— **功能测试全绿，但用户实际用不了**：接口本身是好的（测试直接 POST `/api/students/import` 全通过），
> 可前端选文件那一步的参数用错了，导致**点导入永远静默失败**。
>
> 所以本计划的目标不是"功能存在"，而是：**老师真的按日常用法走一遍时，会不会卡住、会不会被骗、数据对不对。**
>
> **测什么**：用户能不能顺利完成业务 + 中途失败时**能不能知道为什么**。
> **不测什么**：纯接口契约（已有 `e2e-lifecycle.mjs` 80 断言覆盖）。

---

## 一、缺陷分级（本计划的判定口径）

| 级别 | 定义 | 例子 |
|---|---|---|
| **P0 阻断** | 用户**无法完成**业务，且**没有任何提示** | 点导入毫无反应；保存后数据没变也没提示 |
| **P1 严重** | 能完成但**数据错了/丢了**，或提示**误导** | 导入成功但字段丢了；失败却提示"成功" |
| **P2 体验** | 能完成但**用户会怀疑、会重复操作、会看不懂** | 无 loading；提示看不出哪一行错；按钮点了没禁用 |
| **P3 建议** | 不影响完成，但可以更好 | 文案、默认值、排序 |

★ **本计划的核心判据**：**任何一次用户操作，都必须有明确、可理解的结果反馈**（成功 / 失败 / 处理中）。
**"静默"一律按 P0 或 P1 处理** —— 这正是本次用户踩的坑。

## 三、六条业务流程

### 流程 A · 新学员从线索到上课（最完整业务链）

**谁**：admin（招生）+ teacher（上课）
**为什么测**：这是机构的主业务流，跨 5 个模块，任何一环断裂都会让招生流程停下来。

| # | 步骤 | 检查点（不只是"能点"） |
|---|---|---|
| A1 | 招生与报名 → 线索管理 → 新增线索 | 保存后**列表立即出现**该线索；有成功提示 |
| A2 | 线索跟进（改状态/加备注） | 状态变更**立即反映**；备注保存后重新打开还在 |
| A3 | 线索**转化**（填班级/课程/金额） | 转化弹窗**明确告知会创建哪些东西**；转化后线索状态变为"已转化" |
| A4 | 学员管理 → 学生管理 → 查刚转化的学员 | **学员档案已自动创建**且字段完整（姓名/电话/班级/来源渠道） |
| A5 | 财务 → 报班管理 → 查订单 | **订单已自动创建**，金额/课时与转化时填的一致 |
| A6 | 排课与课表 → 周课表 → 找到该班今日课次 | 课次存在且状态为"待上课" |
| A7 | teacher 登录 → 考勤管理 → 考勤登记 → 点名 | 该学员**出现在名单里**；能提交；提交后有成功提示 |
| A8 | 考勤管理 → 考勤记录 → 查今日 | **刚提交的记录可查到**，状态与提交一致 |
| A9 | 财务 → 课消统计 | 课消数增加，与点名扣课一致 |

**★ 关键判据**：A3→A4→A5 的**联动是否真的发生**（跨模块数据一致性）。

---

### 流程 B · 老师的一天（高频日常）

**谁**：teacher
**为什么测**：使用频率最高，体验问题在这里最容易被放大成"系统不好用"。

| # | 步骤 | 检查点 |
|---|---|---|
| B1 | 登录 | 首屏**无白屏、无报错**；菜单与角色匹配（只 5 组） |
| B2 | 首页工作台 | 数据加载有**骨架/loading**；数字非空必错（0 与"暂无"要能区分） |
| B3 | 待办 | 待办列表正常；标记完成有反馈 |
| B4 | 周课表 → 选本周 | 网格**渲染完整**；切周有反馈；课次时间正确 |
| B5 | 课次详情 → 点名 → 批量提交 | 提交有确认/成功提示；**提交后按钮不重复提交** |
| B6 | 请假管理 → 审批一条待审批 | 审批后**状态立即更新**；有提示 |
| B7 | 统计报表 | 出勤率等指标**有数字**（不是空白）；筛选切换有响应 |
| B8 | 连续操作 10 次（切页/切筛选） | **无卡顿、无控制台报错、无数据错乱** |

**★ 关键判据**：B5 的**重复提交防护**与 B8 的**连续操作稳定性**。

---

### 流程 C · 财务月度（钱相关，错不起）

**谁**：admin

| # | 步骤 | 检查点 |
|---|---|---|
| C1 | 报班管理 → 新建订单 | 必填校验有效；保存后**金额显示正确** |
| C2 | 缴费记录 → 登记一笔缴费 | **订单的已缴/剩余课时自动更新**；缴费记录可查 |
| C3 | 退费管理 → 申请退费 → 审批通过 | 审批后**订单余额同步变化**；状态流转正确 |
| C4 | 课消统计 | 按老师/课程/学员三维度**都能切换且有数** |
| C5 | 财务统计 → 欠费查询 | 欠费名单与 C2 的缴费状态**一致** |
| C6 | 经营报表 | 营收数字与缴费记录**对得上**（同一口径） |
| C7 | 交叉验证 | **财务统计的营收 = 经营报表的实收**（同区间；本次已统一出勤率口径，营收口径也要核） |

### 流程 D · 批量数据准备（**用户踩坑的场景，重点**）

**谁**：admin
**为什么测**：用户就在这里反馈"没反应"。这是**本次测试的核心流程**。

| # | 步骤 | 检查点 |
|---|---|---|
| D1 | 学生管理 → 点「模板」 | 下载到文件；**列名与页面解析的列名一致**（不一致＝致命） |
| D2 | 按模板填 3 行（含 1 行班级名不存在） | — |
| D3 | 点「导入」选文件 | **必须给出明确反馈**（成功弹窗 / 错误提示）——**不允许静默** |
| D4 | 修正班级名后重新导入 | 导入成功；**弹窗显示"成功 N 条 / 失败 M 条"** |
| D5 | 导入结果核对 | 列表出现新学员；**模板里每一列都真的落库**（逐列核对，尤其"来源渠道""报名日期"） |
| D6 | 导入重复学号 | **明确提示"学号已存在"**并指出行号；不允许静默跳过 |
| D7 | 导入空文件 / 非 Excel 文件 | 明确提示；不允许无反应 |
| D8 | 直接点「导入」但取消选择文件 | 无异常、无报错 |
| D9 | 导入**同一个文件两次** | 第二次**必须仍有反馈**（哪怕提示"学号已存在"）——不允许"点了没反应" |
| D10 | 大文件（100+ 行） | 有 loading 反馈；不出现长时间无响应 |

**★ 关键判据**：**D3 / D9 是本次用户报的坑**；D5 是"功能可用但数据丢了"的隐蔽坑。

---

### 流程 E · 调课 / 停课 / 补课（异常处理链）

**谁**：admin + teacher

| # | 步骤 | 检查点 |
|---|---|---|
| E1 | 排课模板 → 为某班新增一节排课 | 冲突检测生效（同教师同时段应拦截并说明原因） |
| E2 | 周课表 → 某课次 → 挪课 | 挪课后**原课次显示"已挪课"**、新课次显示"挪课"；双向可跳 |
| E3 | 调课审批（teacher 申请 → admin 审批） | **审批入口与挪课语义不混淆**（已改名区分） |
| E4 | 课次 → 停课 → 恢复 | 状态流转正确；停课期间**点名被拒且有说明** |
| E5 | 补课管理 → 登记补课 → 完成 | **完成时扣课时**；撤销回补；课消数变化正确 |
| E6 | 节次时间改时间 → 已有课次 | **历史课次时间不被回写**（快照语义） |

### 流程 F · 家校沟通（结果输出）

**谁**：admin

| # | 步骤 | 检查点 |
|---|---|---|
| F1 | 成绩管理 → 建考试 → 录成绩 | 录入有反馈；保存后成绩单显示正确 |
| F2 | 学习报告 → 选学员 | **数据完整**（考勤/成绩/课时都对）；无空白区 |
| F3 | 成长档案 → 同一位学员 | 时间线事件与 F1 的操作**对得上** |
| F4 | 通知记录 | 能看到已发送记录；已读状态可操作 |
| F5 | 生成学习报告/通知（如可用） | 生成过程有 loading；生成结果可查看；**失败时有明确原因** |

## 四、执行方式

| 层面 | 手段 | 覆盖 |
|---|---|---|
| **UI 业务流** | Playwright（真实点击，含上传、弹窗、连续操作） | 流程 B/D/F + A 的关键跳转 |
| **接口一致性** | Node 脚本（跨模块数据核对） | 流程 A/C 的联动与对账 |
| **稳定性** | 同一流程**连跑 3 轮**，第 2/3 轮验证幂等与重复操作 | 全部 |

★ **每轮都要检查控制台 `pageerror` 与网络失败请求** —— 很多"没反应"来自被吞掉的异常。

## 五、已知问题（测试中发现并已修复）

> 详细根因、证据与验证结果见 **`业务流测试结果-2026-09-26.md`**。

| # | 问题 | 级别 | 状态 |
|---|---|---|---|
| **BUG-1** | **学生批量导入完全不可用（静默失败）** —— `before-upload` 的参数是 `UploadRawFile`（无 `raw` 字段），代码却读 `file.raw` → FileReader 抛错且未被 try 覆盖 → 0 请求 / 0 提示 | **P0** | ✅ **已修并验证**（含错误班级→明确提示；正确文件→成功弹窗；重复导入→逐行列出原因） |
| **BUG-2** | 模板的「来源渠道」「报名日期」两列**被静默丢弃** | P1 | ✅ 已修（补映射 + Excel 日期序列号兼容） |
| **BUG-3** | 导入无 loading 反馈 | P2 | ✅ 已修（按钮 loading + 防重复提交） |
| **BUG-4** | 导入请求无 `.catch()`、`success:false` 无 else 分支 | P2 | ✅ 已修 |
| **BUG-5** | 模板示例班级名在系统中不存在 | P2 | ✅ 已修（改用系统真实班级名） |

**测试后新增遗留项**（见结果报告 §7）：本地库 **21 条历史测试残留学员**（`QA*`/`PBMU*` 前缀，非本次产生，
会计入统计分母与首页数字）；学习报告「考勤 0 次」与「暂无数据」未区分。
