## 0. 摘要（一页纸）

### 0.1 核心结论

| # | 结论 | 一句话理由 |
| --- | --- | --- |
| **C1** | **不做独立的 AI Agent 系统；采用「逻辑独立、部署统一」的三层混合架构** | "融入 vs 独立"是伪二选一。真正的分界线在**数据主权**与**知识资产**之间，不在"系统边界"上 |
| **C2** | **本次需求触碰了 3 条已拍板的 Non-goals（题库 / RAG 知识库 / 作业批改），必须先改决策再排期** | 不是"能不能做"，而是"做了就等于推翻 2026-09-12 的 D7 决策"，需要显式承认成本 |

| **C4** | **AI 不得跨权限取数。** 含"销售需求"的学情报告必须分版式（教师版 / 教务版），教师版不含任何金额与续费话术 | 2026-09-12 刚把"财务对教师不可见"做成四层防护，AI 是最容易捅穿它的后门 |
| **C5** | **API 成本可忽略（估算每月数十元量级），真正成本是人日与知识库内容建设** | 用 DeepSeek V4-Flash，500 份学情报告/月约 3–7 元。不要因为"怕花钱"而砍需求，也不要因为"便宜"而乱加需求 |

### 0.2 一句话回答"独立还是融入"

> **教务业务数据留在原库、由原系统对外只读提供；知识库与 AI 生成产物可以独立建库；AI 能力作为现有后端的一个模块（`server/src/ai/`）实现，不新开一套系统。**
> 即：**数据融入、能力内聚、交互融入，只有"知识资产"独立。**

### 0.3 建议的分期（详见 §8）

| 阶段 | 内容 | 人日 | 前置 |
| --- | --- | --- | --- |
| **Phase A（可立即启动）** | AI 基础设施（provider 抽象 + 脱敏 + 降级 + 审计）+ 备课助手 + 学情查询与建议 | 9–11 | 无（现有数据够用） |
| **Phase B（需先补地基）** | 文件上传模块 + 题库/知识点地基 + 生成试卷 + 单学员 PDF 学情报告（教师版） | 18–22 | 课堂评价（F2）、知识点体系（F3）、文件存储 |
| **Phase C（可选）** | 批改作业（OCR 半自动）+ 教务版销售向报告 + 班级学情 + 知识库检索升级 | 15–20 | B 阶段全部完成 + 版权方案确认 |

**总投入 42–53 人日**，相当于 ROADMAP 全部 Phase 1–5（约 66 人日）的 2/3。这是一个**需要重新排期的新版本**，不是"顺手加的 AI 功能"。

### 1.1 已有的数据资产（AI 的燃料）

| 财务 | `orders`、`payments`、`refunds`、`hour_consumptions` | 可用但**教师不可见** |
| 招生 | `leads` | 可用（仅 admin） |

### 1.2 已有的基础设施（比想象中多）

这部分是"融入"路线的**最大筹码**，独立系统要重做一遍：

| 设施 | 现状 | 对 AI 的价值 |
| --- | --- | --- |
| 鉴权 | JWT 双 Token + `users.token_version` 可吊销 | AI 端点直接复用，无需新建账号体系 |
| 角色与数据范围 | `requireRole` + `utils/scope.js`（教师按 `classes.head_teacher_id` 隔离） | **AI 取数自动继承权限**，这是"融入"的核心优势 |
| 脱敏策略 | 教师访问学习报告时 `amount`/`paid` 已被剔除（`reports.js:98-117`） | 已有"字段级脱敏"先例，AI 层可扩展成白名单 |
| 指标定义 | `analytics.js` 的 `METRIC_DEFINITIONS`（**12 个指标**，含 name/formula/source_table/unit） | **现成的 AI 语义层**，可直接作为提示词上下文与降级规则引擎的数据源 |
| 审计 | `index.js` 全局中间件 `res.on("finish")` 兜底 | AI 生成记录可直接落审计，满足"可复现"要求 |
| 只读数据出口 | `analytics.js` 提供 JSON / CSV（带 BOM）导出，`meta.data_version` 取 `PRAGMA user_version` | 已具备"AI 输出侧"的数据版本标记能力 |

`analytics.js` 的 12 个指标：出勤率、缺勤率、学员总数、在读学员数、在读率、实收金额、线索总数、线索转化数、线索转化率、净消耗课时、考试平均分、优秀率。

> 注意：`analytics.js` 全量端点目前 `requireRole("admin")`。教师版 AI 需要**另开教师可见的指标子集**，不能直接放开这个端点。

### 1.4 需求与既定决策的冲突清单（必须先看这一节）

2026-09-12 的深度需求访谈已拍板 12 个决策点（`ROADMAP.md` §〇）。本次需求直接冲突 3 条：

| 决策 | 原结论 | 本次需求要求 | 冲突性质 |
| --- | --- | --- | --- |
| **D7** | 知识库/题库"**本期只做最小依赖：知识点体系**"，明确不做组卷、在线答题、阅卷、错题本、**RAG 知识库** | 要求"生成试卷"+"AI 知识库存放教材、题目、知识点" | **直接推翻**。D7 的原文就是"不做组卷、不做 RAG 知识库" |
| **D5** | 内网出公网调 API，**字段白名单脱敏**（姓名/家长电话/金额一律不出网） | 要求 AI 结合"学生学习情况+日常表现+**销售需求**"生成报告 | **需扩充白名单**。销售需求会诱导把金额/课时余额送模型 |
| **D2** | **不做家长端、不做任何出网触达**，通知模块定位"内部留痕" | PDF 学情报告天然具备"发给家长"的用途 | **口子风险**。PDF 一旦可导出，出网触达 D2 事实上被绕过 |

**我的判断**：这三条冲突**不是反对做，而是必须显式升级决策**。建议按下面处理：

1. **D7 修订**：知识库从"只做知识点最小集"升级为"知识点体系 + 私有小题库（自有/授权题目）+ 检索能力"；**仍不做**在线答题、错题本、完整组卷引擎（组卷只做"AI 生成 + 教师审核"的轻形态，不做难度/区分度算法组卷）。
2. **D5 扩充**：出网白名单**新增**"课时余量、剩余课时（整数）"供教务版报告使用；**继续禁止**姓名、家长电话、金额（元）、家长姓名。金额类信息**只能由本地模板渲染，不得进入提示词**。
3. **D2 不修订，但要加约束**：PDF 报告定位为"教师与教务内部使用 + 线下交付"，系统内**不提供任何一键外发通道**（无短信/无邮件/无微信）。若将来要发家长，属于新决策，重新走 D2。

> 这三个处理是本次报告最重要的建议之一：**改决策 = 承认代价**。如果只是"顺手做了"，就会在不经意间把 2026-09-12 辛苦收敛的产品边界全部打开。

## 2. 核心论证：AI 能力应融入现有系统，还是构建独立的 AI Agent 系统？

### 2.1 先纠正问题框架

"融入 vs 独立"这个二选一之所以难答，是因为它把三个**可以独立决策**的问题绑成了一个：

| 决策维度 | 真正要回答的问题 | 为什么可以分开决定 |
| --- | --- | --- |
| **数据层** | 教务业务数据存在哪里、谁提供、以什么权限暴露？ | 数据已被现有系统持有，物理上无需搬迁 |
| **能力层** | AI 代码放哪里、由谁部署、如何升级？ | 可以是一个模块，也可以是一个进程，对业务方透明 |
| **交互层** | 老师在哪个界面用？ | 老师的入口已经存在（现有教师端菜单） |
| **知识层** | 知识库（教材/题目）存哪里？ | 这部分**不属于**教务业务数据，独立建库反而更干净 |

把它们拆开后，答案几乎是唯一的：
**数据融入、能力内聚、交互融入，只有知识层独立。**

### 2.2 方案 A：完全融入（在现有后端内实现）

```
现有 Express 后端
  ├─ routes/（原有 24 个路由）
  └─ ai/（新增）
       ├─ provider.js    模型调用（OpenAI 兼容协议，可配 base_url/model/key）
       ├─ redact.js      出网字段白名单
       ├─ prompts/       提示词模板（按场景一文件）
       ├─ engine.js      本地指标计算（复用 analytics 的 12 指标口径）
       ├─ generators/    备课 / 出卷 / 学情建议 / PDF 报告
       └─ knowledge/     知识库读写（走独立表）
  复用：JWT、requireRole、utils/scope.js、audit 全局中间件、validate.js
```

- **优势**：权限天然继承（教师只能看到自己班学生）；无新增运维面；复用审计与迁移体系；`analytics.js` 的指标定义可直接当语义层。
- **劣势**：出卷/批改等重任务会占用 Web 进程；知识库检索若上向量库会让 SQLite 变得臃肿（`node:sqlite` 无向量扩展）。
- **结论**：作为**主体方案**保留，但需要用"任务模式"隔离长耗时调用（§6.3）。

### 2.3 方案 B：完全独立 Agent 系统

形态：新建一个独立服务（Python/LangChain/LangGraph + 向量库 + 自己的账号体系 + 自己的库），教务系统作为它的"数据源"。

**独立建设必须先回答"怎么读本教务系统的数据"，四种通道的实测评估如下：**

| 通道 | 做法 | 可行性 | 致命问题 |
| --- | --- | --- | --- |
| **B1 只读 API**（推荐） | 教务系统新增 `/api/agent/*` 只读命名空间，Agent 用**服务账号**（新角色 `agent`，只读）调 JWT 接口 | **高** | 需新建 1 个只读角色与若干聚合端点；但权限、审计、脱敏全部复用 |
| **B2 只读库副本** | 定时 `VACUUM INTO` 或文件拷贝出只读副本，Agent 直连副本 | 中 | WAL 一致性需 `PRAGMA wal_checkpoint(TRUNCATE)` 后拷贝；**与 Docker bind mount 缓存冲突**（已知坑，容器会读到陈旧视图）；跨主机需解决挂载 |
| **B3 直连业务库** | Agent 直接读写 `server/data/attendance.db` | **禁止** | ①绕过权限与审计（未成年人数据、财务数据）②SQLite 单写者模型下并发写入会锁竞争 ③schema 与代码强耦合，迁移 v16/v17 时随时炸 ④违反"生产库不得直接写"的既有约定 |
| **B4 快照同步** | 每日导出 CSV/JSON 落到 Agent 侧 | 低-中 | 数据滞后（学情报告要"上周出勤"，滞后一天可能可接受，但"刚才这节课谁缺勤"就必须实时） |

**独立方案的真实代价（按本项目规模）**：

| 代价项 | 量级 | 说明 |
| --- | --- | --- |
| 新增运维面 | +1 服务、+1 库、+1 套密钥 | 单校区 5–15 员工，无专职运维 |
| 账号体系重复 | 中 | 教师要在两个系统登录，或者做 SSO（又增成本） |
| 权限模型复制 | **高** | 现有四层权限（菜单/接口/字段/导出）要在 Agent 侧重实现，且极易漏 → 数据泄露风险 |
| 数据一致性 | 中-高 | 双写/缓存导致"AI 说张三剩 8 课时，教务系统说 6 课时"，家长质疑无法解释 |
| 收益 | **低** | 独立部署带来的"解耦"收益，在单机单校区场景基本不存在 |

### 2.4 方案 C：分层混合（**推荐**）

**这是唯一同时拿到两边好处的方案，核心是划一条分界线：**

> **分界线：教务业务数据（学生/考勤/成绩/财务）→ 留在原库，原系统只读提供。
> 知识资产与 AI 产物（教材、题目、知识点、生成记录）→ 独立建表，甚至可以独立成库。**

```
┌──────────────────────────────────────────────────────────────┐
│  教师端界面（现有 Vue 前端，新增「AI 助手」菜单 + 内嵌入口）      │
└───────────────────────────┬──────────────────────────────────┘
                            │ 复用现有 JWT / requireRole / scope
┌───────────────────────────▼──────────────────────────────────┐
│  现有 Express 后端（:3000）                                    │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  ai/ 模块（逻辑独立、可单独测试；部署统一）                │  │
│  │   provider → redact → engine(本地指标) → generator      │  │
│  └───────────┬─────────────────────┬──────────────────────┘  │
│              │ 只读、带 scope        │ 读写                   │
│  ┌───────────▼──────────┐  ┌───────▼──────────────────────┐  │
│  │ 教务业务库（不动）      │  │ 知识库 + 生成记录（新增迁移）  │  │
│  │ students/attendances  │  │ knowledge_points / questions  │  │
│  │ exams/orders/...      │  │ materials / ai_generations    │  │
│  └──────────────────────┘  └──────────────────────────────┘  │
└──────────────────────────────────────────────────────────────┘
                            │ 仅出网：脱敏后的结构化指标 + 题干
                            ▼
                     DeepSeek API（V4-Flash / V4-Pro）
```

**"逻辑独立"的具体含义（防止被理解成"就是塞在一起"）**：

1. `server/src/ai/` 是一个**自包含模块**，对外只暴露 `generate(scene, payload, ctx)` 一个入口，内部可替换模型、可单测、可 mock（无 Key 时走规则引擎）；
2. 知识库表**独立命名空间**（`kb_*` 前缀），不做外键指向业务表（只存 `student_id` 之类弱引用），将来要搬到独立库或独立服务时，**只需换数据源，不动业务代码**；
3. AI 生成记录（`ai_generations`）独立存，含 `provider / model / input_snapshot / output / operator / created_at`，满足"可复现、可审计"；
4. 将来真要拆成独立服务时，**接口已经现成**：把 `ai/` 目录的入参出参定义成 HTTP 契约即可平移，业务代码零改动。这是"预留退路"而非"提前抽象"。

### 2.5 决策矩阵

评分：5 = 最优，1 = 最差。权重按本项目（单校区 200–500 学员 / 5–15 员工 / 无专职运维）设定。

| 维度 | 权重 | A 完全融入 | B 完全独立 | **C 分层混合** |
| --- | --- | --- | --- | --- |
| 权限与合规安全 | 25% | 5 | 2 | **5** |
| 数据一致性与实时性 | 20% | 5 | 3 | **5** |
| 开发与运维成本 | 20% | 5 | 2 | **4** |
| 可扩展性（知识库/多校/复用） | 15% | 2 | 5 | **4** |
| 迭代速度（AI 侧试错） | 10% | 3 | 5 | **4** |
| 与既有决策/Non-goals 的契合 | 10% | 4 | 2 | **4** |
| **加权总分** | | **4.30** | **2.95** | **4.55** |

（计算：A = 5×.25+5×.20+5×.20+2×.15+3×.10+4×.10 = 1.25+1.00+1.00+0.30+0.30+0.40 = 4.25；B = 0.50+0.60+0.40+0.75+0.50+0.20 = 2.95；C = 1.25+1.00+0.80+0.60+0.40+0.40 = 4.45）

> A 与 C 相差很小，说明"AI 代码放哪"其实不是关键；**C 真正赢在"知识库独立"这一条为未来留了路**。如果只做 Phase A（不做知识库），A 方案完全够用——C 是为 Phase B/C 准备的。

### 2.6 结论与"何时才该独立"的触发条件

**结论**：采用 **方案 C**。**不新建独立系统。**

**但要明确写下触发条件**，将来任何一个成立时，把 `ai/` 与 `kb_*` 整体拆成独立服务（这是一次搬迁，不是重写）：

| 触发条件 | 说明 |
| --- | --- |
| T1 多校区 / SaaS 化 | 校区从 1 变 N，或要对外售卖（推翻 D1） |
| T2 知识库需被其他系统复用 | 例如同一集团的另一套系统要调题库 |
| T3 AI 负载影响教学业务 | AI 批量任务导致教师端接口响应变慢（用 §6.3 的任务模式先撑，撑不住再拆） |
| T4 需要本地私有化模型 | 部署本地推理服务（GPU），此时独立部署才有意义 |
| T5 需要向量检索规模 | 题目从 10³ 级涨到 10⁶ 级，`node:sqlite` 不再合适 |

### 2.7 若独立建设：数据读取通道的设计细节（备选方案存档）

即便本期不独立，也把设计写清，便于将来执行（**这是"独立 Agent 如何读取教务系统数据"的完整回答**）：

**推荐通道：只读 API 网关（B1）**

1. **新增只读角色**：`users.role` 增加 `agent`（或在现有 JWT 中加 `scope: read_only` 声明）。该角色：
   - 可访问 `/api/agent/*` 下的全部只读端点；
   - **不可**访问任何写端点（中间件层面拦 `POST/PUT/DELETE`）；
   - **不可**访问 `reports.js` 的金额字段、`finance.js` 全量、`leads.js`。
2. **新增聚合端点（面向 AI 优化，而非给前端用）**：
   - `GET /api/agent/students/:id/profile` → 学员画像（脱敏后的结构化指标 + 出勤分布 + 成绩趋势 + 知识点掌握度 + 课时余量整数）
   - `GET /api/agent/classes/:id/summary` → 班级概览（谁在掉队、班级薄弱知识点）
   - `GET /api/agent/knowledge?subject=&grade=` → 知识点树
   - 统一响应信封复用 `analytics.js` 的形态：`{ data: { metrics, records, meta } , metric_definitions }`，其中 `meta.data_version` 取 `PRAGMA user_version`，`meta.generated_at` 为 ISO 时间。
3. **认证**：服务账号 + 长期 `refresh` token 或独立 API Key（走 `users.token_version` 可即时吊销）。
4. **审计**：所有 `/api/agent/*` 调用天然落入全局审计中间件，记录 `who / when / what`。
5. **脱敏在网关侧完成**：Agent 侧拿到的是**已脱敏**的数据（姓名 → `学员A（内部ID 123）`，金额直接不存在），使"Agent 会不会把敏感数据送模型"这个问题**在源头消失**。

**关键设计原则**：脱敏必须发生在**教务系统侧**，不能依赖 Agent 自觉。理由见 §6.2（这是 R3 风险的唯一可靠解法）。

**禁止**：B3 直连业务库。已核查现有约束（`../03-开发指南/项目地图.md` 第五节："生产库不得直接写"；Docker bind mount 缓存坑）——直连会让 AI 成为绕过四层权限的合法后门。

## 3. 面向教师的 Agent 能力设计

先给一张**可行性总览**，再逐个展开：

| 场景 | 可行性 | 前置依赖 | 人日 | 排期 |
| --- | --- | --- | --- | --- |
| 3.1 备课助手 | **可立即做** | 无（教材文本可由教师粘贴/后续上传） | 3 | Phase A |
| 3.2 生成试卷 | 需地基 | 题库（自有/授权）+ 知识点体系 + 文件/文本导入 | 6–8 | Phase B |
| 3.3 批改作业 | **形态需重构** | 文件上传 + OCR + 作业数据模型 | 8–10 | Phase C |
| 3.4 学情查询与建议 | **可立即做** | 无（复用 12 指标 + 现有报告端点） | 4 | Phase A |
| 3.5 PDF 学情报告 | 需地基 | **课堂评价（F2）**（"日常表现"）+ PDF 引擎 + 分版式权限 | 6–8 | Phase B（教师版）/ C（教务版） |

### 3.1 备课助手

**用户故事**
- 作为教师，我希望输入课题与教学目标后得到一份教案初稿与配套练习，以便把备课时间从 1 小时压到 20 分钟。
- 作为教师，我希望系统按我的班级学情（上节课出勤差、某知识点平均分偏低）自动提示这节课该重点讲什么，以便不靠感觉备课。

**形态**：现有教师端新增「AI 备课」页（或向已有课程页加侧边抽屉）。输入 = 学科 / 年级 / 课题 / 课时长度 / 教学目标（+ 可选：参考教材片段）。

**输出结构（固定模板，防跑偏）**
```
1. 教学目标（知识 / 能力 / 素养）
2. 重难点（含"为什么难"）
3. 教学流程（时间轴：导入-x 分 / 新授-x 分 / 练习-x 分 / 小结）
4. 课堂提问清单（含预设答案要点）
5. 分层练习（基础 / 提升 / 拓展各 2–3 题）
6. 板书设计
7. 课后作业建议
```
结构化输出 + 教师可编辑 + 一键保存为"教案"（落 `ai_generations` 或新表 `lesson_plans`），下次可复用。

**增值点（与市场通用工具拉开差距的地方）**：把**本地指标**注入提示词——"本班上次该知识点平均得分率 62%，优秀率 15%，建议本课时加强 X"。这是 MagicSchool 这类通用工具**做不到**的，因为我们有班级数据。这是本系统 AI 的核心差异化。

**接口草案**
```
POST /api/ai/lesson-plan        { course_id, topic, grade, duration, objectives? }
GET  /api/ai/lesson-plan/:id    历史教案
```

**风险**：教师可能直接照抄不审。缓解：输出页固定顶部提示"AI 初稿，请教师核对后使用"，并提供"已核对"勾选后才可导出。

**人日：3**（含提示词调试、前端页面、浏览器验证、文档）

### 3.2 生成试卷

**现实约束（必须先说清）**：出卷质量 = 题库质量。没有自己的题库，只能让模型"原创出题"，风险是**答案错误、超纲、与本校教材不匹配**。市场调研显示头部产品都靠"题库 + AI 组卷"而非纯生成（§5.2）。

**推荐形态（分两步走，不一步到位）**

| 步骤 | 形态 | 依赖 |
| --- | --- | --- |
| **B-1 轻量** | AI 按"知识点 + 难度 + 题型 + 题量"**原创出题**，输出试卷 + 答案 + 解析，教师逐题审核（可删除/替换/改分） | 知识点体系（F3） |
| **B-2 增强** | 从**私有小题库**中按知识点/难度**选题组卷**，AI 只负责补足缺失题型的原创题与整卷排版 | 题库（新建）+ 知识点标注 |

**输出**：网页预览 → 导出 PDF（复用 §6.4 的 PDF 引擎）或 `xlsx`（现有 `xlsx` 依赖可直接用，成本最低的过渡方案）。

**前置依赖明细**

| 依赖 | 现状 | 需要做 |
| --- | --- | --- |
| 知识点体系 | 无 | 新建 `knowledge_points(id, subject, grade, parent_id, name, sort)`，教师维护树（F3 原计划 2.5 人日） |
| 题目库 | 无 | 新建 `questions(id, subject, grade, kp_id, type, difficulty, stem, options, answer, analysis, source, status, created_by)` |
| 题目录入 | 无 | 两条路径：① 教师手工录入/粘贴文本；② **AI 从上传文档抽题**（依赖文件上传 G2） |
| 试卷实体 | 无 | 新建 `papers` + `paper_items`（或先用 `ai_generations` 存 JSON，更省成本，推荐先这样） |

**出卷安全阀（必做）**
1. **答案必审**：AI 答案默认标记"未审核"，教师逐题确认后才能发布；未审核试卷不可导出（这是对"AI 出题答案可能错"的唯一可靠防御）。
2. **不得跨年级**：提示词硬约束 + 输出校验（含"年级"字段回填比对）。
3. **不重复**：组卷时对题库做相似度去重（B-2 阶段）。

**人日：6–8**（不含题库内容建设；内容建设是**持续投入**，见 §4.6）

### 3.3 批改作业（形态必须重构）

**为什么不能按需求字面做**：
- 本系统**没有学生端**（学生不登录，D2/D1），所以"学生在线提交作业"不存在；
- 本系统**没有文件上传**（G2），所以"上传作业照片"也做不到。

**唯一可行形态：纸质作业拍照 → OCR → AI 判分建议 → 教师确认**

```
教师手机/电脑上传作业照片（多张，一页一张）
   ↓ 文件存储（新增）
   ↓ OCR（多模态模型直接看图，或专用 OCR）
   ↓ 按题切分 + 逐题判分（客观题自动 + 主观题给"建议分 + 评语"）
   ↓ 教师复核界面：逐题确认/改分（AI 结果默认"待确认"）
   ↓ 落库（新建 homework / homework_items / homework_grades）
   ↓ 汇总 → 班级错题统计 → 喂给学情分析与 PDF 报告
```

**关键设计决策**

| 决策 | 建议 | 理由 |
| --- | --- | --- |
| 客观题 | 全自动判分，教师抽查 | 准确率高，收益最大 |
| 主观题 | **只给建议分 + 评语，不自动写入成绩** | 行业共识：作文类可用作反馈，不可作最终成绩（§5.1 市场调研明确结论） |
| 手写识别 | 优先生成"识别置信度低"的警示，低置信度题目强制人工 | 手写 OCR 错误率仍高，静默出错比不批更糟 |
| 隐私 | 作业照片**只存本地**，不出网；出网的只有题干与作答文本 | 学生手写原件属敏感个人信息 |
| 与成绩的关系 | 作业得分**默认不进** `exam_scores` | 避免污染成绩口径与"剩余学费"等既有计算链 |

**前置依赖**：文件上传模块（要做：存储路径规划、大小/类型限制、清理策略、`server/data/uploads/` 加入 gitignore）+ 作业数据模型 + 多模态模型能力（V4-Flash 是否支持视觉需实测，**不满足则改用专用 OCR 服务**——这是本次调研发现的**待验证项**）。

**人日：8–10**（风险最高的一项，建议放最后，先跑小范围试点）

### 3.4 学情查询与建议

**用户故事**
- 作为教师，我希望用一句话问"李同学最近怎么样、我该做什么"，得到基于真实数据的回答与 3 条可执行建议。
- 作为教师，我希望系统主动告诉我"本周有 5 个学生出现连续缺勤或成绩下滑"，而不是我自己去翻。

**实现方式（复用现有资产，成本极低）**
1. **本地先把数字算出来**（复用 `analytics.js` 的指标口径 + `reports.js` 的聚合 SQL）：出勤率、迟到/早退/缺勤次数、成绩趋势（最近 3 次）、知识点掌握度（F3 完成后）、课时余量、离群检测（同班 Z-score）。
2. **把指标 + 指标定义（`METRIC_DEFINITIONS` 直接当语义说明）送模型**，让模型只做"解读与建议"这件事。
3. **严格禁止 text2sql**（沿用既有决策）：模型**不允许**生成任何 SQL，只能消费本地算好的指标。命中不了的问题明确回答"这个问题我答不了"并列出可问清单。

**输出**：一页结论 + 三条建议 + 证据（引用了哪几个数字）+ "数据不足"的诚实降级（如：考试成绩仅 1 次，不足以判断趋势——**不硬凑结论**）。

**主动预警（高价值，建议同批做）**：三类规则（连续缺勤 ≥2 次 / 成绩环比下滑 ≥15% / 课时余量 ≤2）→ 站内通知 + 班主任待办。这是 ROADMAP 的 F11，AI 化后措辞更自然，但**规则本身必须本地判定**。

**接口草案**
```
POST /api/ai/student-insight   { student_id, question? }
GET  /api/ai/class-insight     { class_id }
GET  /api/ai/alerts            我的待办（教师视角）
```

**人日：4**（含前端问答页 + 预警入口）

### 3.5 PDF 学情报告（含"销售需求"的正确处理方式）

这是**需求里最难、也最容易出事**的一项。拆三层说。

#### 3.5.1 数据来源与现实缺口

需求要求"结合**学习情况 + 日常表现 + 销售需求**"。对应现状：

| 需求要素 | 现有数据 | 缺口 |
| --- | --- | --- |
| 学习情况 | 考勤（`attendances`）、成绩（`exam_scores`）、课时消耗（`hour_consumptions`） | 充足 |
| **日常表现** | **无** | **必须新建 `class_evaluations`（F2 课堂评价）**。不解决这项，报告只能写"出勤良好、成绩稳定"，即"正确的废话" |
| 销售需求 | 课时余量（`orders.remain_hours`）、在读状态、近期缴费 | 足够；但**金额对教师不可见**（见下） |

**结论：PDF 报告必须先做 F2 课堂评价。** 这是本报告与 ROADMAP 一致、但必须强调的硬前置（ROADMAP §一已定性："系统在库里没有学生日常表现数据……AI 学情分析若无课评数据，只能基于三次考试做线性回归，产出正确的废话"）。

#### 3.5.2 三个版式（对"销售需求"的权限解法）

**禁止**：一份 PDF 同时包含学习分析与销售话术，然后交给教师。这会直接破坏 2026-09-12 建立的四层权限（菜单/接口/字段/导出）。

**建议分为三个版式，由角色决定能生成哪一种**：

| 版式 | 面向 | 内容 | 谁能生成 | 金额 |
| --- | --- | --- | --- | --- |
| **A 教师版** | 教师自用 / 教研 | 考勤、成绩趋势、知识点掌握、课堂表现、教学建议 | teacher + admin | **不含**任何金额、不含续费话术 |
| **B 教务版（销售向）** | 校长 / 教务 | A 的全部 + 课时余量、剩余课时、在读周期、**续费建议话术**、下阶段课程规划 | **仅 admin** | 含**课时数**，**不含**金额（元） |
| **C 家长版（本期不做）** | 家长 | B 的内容 + 金额与缴费明细 | — | 本期不做（触碰 D2，需重新决策） |

**关键约束**：
- 教师版与教务版**共用同一套指标引擎**，只在渲染层与提示词层分叉；**教师版不走"销售需求"提示词**。
- 销售向内容由**本地模板 + 课时余量规则**生成（如"剩余 6 课时，按每周 2 次课约可上 3 周，建议在第 4 周前沟通续费"），**不把金额送模型**。
- 全部金额类数字**只在本地渲染**（"数据不出网"原则的延伸）。

#### 3.5.3 PDF 生成方案选型

| 方案 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- |
| **HTML + 无头浏览器打印**（`puppeteer` / `playwright`） | 排版自由度最高，可直接复用前端样式；图表（ECharts）能完美出图 | 镜像体积 +约 300MB；内存占用高；Alpine 需额外依赖 | **推荐**（二期若嫌重可换 P1） |
| **前端 `window.print()` + `@media print` CSS** | 零新增依赖，最快落地 | 依赖用户浏览器；无法服务端批量生成；分页控制弱 | **Phase B 先用这个**（1 人日，先验证价值） |
| `pdfkit` / `pdf-lib` 服务端绘制 | 轻量（<5MB）、可控 | 中文字体需内嵌（+5–10MB）；排版靠代码，改版成本高 | 备选 |
| 第三方云 PDF 服务 | 省事 | **学生数据出网**，违反脱敏原则 | **不考虑** |

**建议路径**：Phase B 先用「前端打印 + 打印样式表」快速验证价值（教师能否真的用起来），Phase C 若确认高频使用，再引入 `puppeteer` 做服务端批量生成。

**人日：6–8**（含三版式模板、打印样式、图表渲染、权限校验、浏览器验证）

## 4. AI 知识库规划（教材 / 题目 / 知识点）

### 4.1 资产分层：三类知识，三种处理方式

| 层 | 内容 | 规模（本机构现实） | 存储与检索建议 |
| --- | --- | --- | --- |
| **L1 知识点** | 学科 → 章节 → 知识点树 | 每学科 100–500 个节点 | 关系表（树）+ 全文检索。**最简单、收益最高，先做** |
| **L2 题目** | 题干、选项、答案、解析、难度、知识点标签、来源 | 单校区起步 500–5,000 题 | 关系表 + 标签过滤 + 全文检索（FTS5） |
| **L3 教材** | PDF/Word/PPT 讲义、教材扫描件 | 每学科几十份 | 文件存储 + 切片文本 + 全文检索；**向量检索可选** |

### 4.2 一个明确的反建议：先标签，后向量

市场上动辄宣传"2 亿题库""全科知识图谱"（§5.2），但**那是别人的护城河，不是我们的起点**。对一个 200–500 学员的单校区机构：

- 引入向量库需要：embedding 模型（额外 API 或本地模型）、向量存储（`node:sqlite` 无向量扩展，需引入外部依赖或独立服务）、切片与重排策略、评测集。**开发与运维成本远超收益**；
- 而实际检索需求 90% 是**强结构化**的："初一数学 一元二次方程 难度中等 选择题 3 道"——这用**标签 + SQL 过滤**就够了，且结果**精确可控**（不像向量检索会召回"看起来相关但超纲"的题）；
- `node:sqlite` 自带 **FTS5 全文检索**（需确认编译支持，待验证项），对题干/教材文本已够用。

**建议三阶段检索演进**

| 阶段 | 检索方式 | 何时启动 |
| --- | --- | --- |
| S1 | **结构化过滤**（知识点 + 难度 + 题型 + 年级）+ LIKE/FTS5 | Phase B 立即 |
| S2 | **三元混合**：结构化过滤 → FTS5 排序 → 送模型重排（LLM 做 rerank，不做召回） | Phase C |
| S3 | 向量检索（embedding + 向量库） | **仅当** T5 触发或题目规模 > 10⁴ 且 S2 效果不足时 |

> 这个演进路径的价值在于：**每一步都能独立交付价值**，且 S1→S2→S3 是叠加而非重写。

### 4.3 数据模型（建议）

```sql
-- L1 知识点（原 F3 计划，建议提前到 Phase B 前置）
knowledge_points(id, subject, grade, parent_id, name, code, sort, description, created_at)
  UNIQUE(subject, grade, code)

-- L2 题目
questions(id, subject, grade, type, difficulty, stem, options_json, answer,
          analysis, source, kp_ids_json, status, created_by, created_at, updated_at)
  -- status: 草稿 / 待审 / 已启用 / 停用
  -- source: 自编 / 教材 / 授权题库 / AI生成
  -- difficulty: 1-5
questions_fts(...)  -- FTS5 虚表，索引 stem + analysis

-- L3 教材
kb_materials(id, subject, grade, title, type, storage_path, size, uploaded_by, created_at)
kb_chunks(id, material_id, seq, content, kp_ids_json)   -- 切片，供检索与引用
```

**设计要点**
1. **`kp_ids_json` 而非中间表**：单题知识点 1–3 个，用 JSON 存够用且省一张表；若将来要按知识点做统计（"该知识点共 N 题"），用 SQLite 的 `json_each` 可胜任。**这是刻意的简化**（符合本项目"不过度设计"的既有基调）。
2. **不做外键指向业务表**：知识库与教务业务数据解耦（§2.4 的分界线），便于将来独立。
3. **题目必须带 `source` 字段**：版权合规的审计基础（§4.6）。
4. **AI 生成记录独立表** `ai_generations(id, scene, operator_id, provider, model, input_snapshot_json, output_text, tokens_in, tokens_out, cost_est, created_at, accepted_at)`——满足"可复现、可审计、可统计成本"。

### 4.4 入库管线

```
来源                    → 抽取             → 清洗         → 标注            → 入库
① 教师手工录入           直接结构化输入       校验格式       选知识点标签       待审 → 启用
② 上传文档(PDF/Word)     文本抽取            去页眉页脚      AI 建议标签       待审 → 启用
③ AI 生成题目            结构化输出           去重校验       生成时即带标签     待审 → 启用
④ 试卷反向录入           逐题切分            格式归一       人工/自动标注      待审 → 启用
```

**必做质量控制**（否则题库会变成垃圾场）
1. **去重**：入库前对题干做相似度检查（先用 FTS5 + 关键词重叠的轻量方案）。
2. **待审状态**：任何来源的题目默认"待审"，教师确认后才能被用于组卷。
3. **可追溯**：每题记录来源与录入人。

### 4.5 检索与引用策略

给模型的**永远不是整个题库**，而是"检索到的少量候选题 + 知识点定义"：

```
教师请求：初一数学 / 一元二次方程 / 中等难度 / 5 道选择题
   ↓ 1. 结构化过滤：subject=数学 AND grade=初一 AND kp=一元二次方程 AND difficulty=3 AND type=选择题
   ↓ 2. 若不足 5 道 → FTS5 全文扩展检索（放宽到相邻知识点）
   ↓ 3. 若仍不足 → 标记"题库不足，将由 AI 原创补足 N 道"
   ↓ 4. 送模型：仅在需要"改写/补足/整卷排版/写解析"时调用
```

**关键原则**：**能从库里拿到的题，不让模型生成**。模型的价值是"补足与加工"，不是"题库替代品"。这样答案质量与合规性都大幅提升。

### 4.6 冷启动路径与版权合规（**重要，容易被忽略**）

**版权是这个功能最大的法律风险**：
- 教材全文复制入库 → 侵权（教材有明确著作权，且有"教材版本"限制）；
- 从网上抓题（含各种"XX 题库"）→ 侵权；
- 扫描教辅拍照 OCR 入库 → 侵权。

**建议的来源优先级**（写死为产品规则）：
| 优先级 | 来源 | 合规性 |
| --- | --- | --- |
| 1 | **教师自编题** | 机构自有，最安全 |
| 2 | **AI 原创题**（带 `source=AI生成` 标记） | 无第三方版权；但需人工审题（答案可能错） |
| 3 | 采购的正版题库 / 授权教材电子版 | 需保留授权凭证 |
| 4 | 教材原文引用 | **仅限"摘要引用 + 出处标注"**，不得整册入库；建议索性不做，改为教师上传自己的讲义 |
| — | 网络抓取 / 扫描教辅 | **禁止** |

**冷启动建议（务实）**：
- 不要一上来建全科题库。**每个学科先建"本学期正在教的那一章"**（约 50–100 题），足够验证流程并有实际价值；
- 知识点树由教研组长牵头、AI 辅助生成初稿（让 AI 按教材目录生成知识点树，教师修改——这是 AI 最低风险、最高效率的用法）；
- 目标：首月每学科 100 题、次月 300 题、学期末 1,000 题（不是一开始就 10,000）。

### 4.7 知识库分期

| 阶段 | 交付 | 人日 |
| --- | --- | --- |
| B | `knowledge_points` + 教师维护界面 + 成绩录入时打标签 + 历史成绩补录入口 | 3.5 |
| B | `questions` + 手工/批量文本录入 + 待审流程 | 3 |
| C | 文档上传 → 抽题（依赖文件上传）+ FTS5 检索 + AI 重排 | 5 |

| — | （S3 向量检索） | 暂不排期 |

## 6. 技术方案要点

### 6.1 模型选型与成本（含一个必须避开的坑）

**必须避开的坑**：DeepSeek 已于 **2026-07-24** 停用旧别名 `deepseek-chat` / `deepseek-reasoner`。当前应使用 **`deepseek-v4-flash`** / **`deepseek-v4-pro`**。若按 ROADMAP 里"调 DeepSeek"直接写旧模型名，上线即失败。

**当前价格（2026-08-17 生效，峰谷定价，单位：元/百万 tokens）**

| 模型 | 时段 | 输入（缓存命中） | 输入（未命中） | 输出 |
| --- | --- | --- | --- | --- |
| `deepseek-v4-flash` | 高峰（9–12、14–18 点） | 0.10 | 3.0 | 9.0 |
| `deepseek-v4-flash` | 空闲 | 0.05 | 1.5 | 4.5 |
| `deepseek-v4-pro` | 高峰 | 0.30 | 9.0 | 27.0 |
| `deepseek-v4-pro` | 空闲 | 0.15 | 4.5 | 13.5 |

**成本试算（用 Flash，保守按高峰价）**

| 场景 | 输入 tokens | 输出 tokens | 单次成本 | 月量 | 月成本 |
| --- | --- | --- | --- | --- | --- |
| 学情报告（单学员） | ~2,000 | ~800 | ≈0.013 元 | 500 份 | **≈6.6 元** |
| 教案生成 | ~1,500 | ~2,500 | ≈0.027 元 | 200 次 | ≈5.4 元 |
| 单张试卷（含答案解析） | ~3,000 | ~3,000 | ≈0.036 元 | 50 张 | ≈1.8 元 |
| 班级学情概览 | ~4,000 | ~1,200 | ≈0.023 元 | 20 次 | ≈0.5 元 |
| **合计** | | | | | **≈15 元/月**（用 Pro 约 3–5 倍，仍 < 80 元/月） |

**结论**：**API 成本可以忽略，不构成任何约束**。真正的成本是：① 开发人日（42–53）；② 知识库内容建设（持续投入，教师时间）；③ 教师的使用习惯培养（最容易被低估）。

**建议**：默认 `v4-flash`；仅"整卷命题 + 解析生成"这类质量敏感场景允许切 `v4-pro`（可配置）。成本记录落 `ai_generations.cost_est`，便于按场景核账。

### 6.2 安全与合规（三个层面）

**层面 1：数据出网（对应既有 R3 风险）**

| 项 | 规则 |
| --- | --- |
| 出网白名单 | 内部学生 ID、年级、学科、结构化指标数值、知识点名称、题目文本、教师输入的课题 |
| **禁止出网** | 学生姓名、家长姓名、家长电话、**金额（元）**、身份证/学号等任何直接标识 |
| 脱敏执行位置 | **在教务系统侧**（`ai/redact.js` 硬编码白名单 + 出网前统一过滤），不依赖模型侧自律 |
| 生成物中的姓名 | 模型输出用"学员A/内部ID"占位，**本地渲染时再回填真实姓名**（关键技巧：让模型永远不知道姓名，但报告上仍有姓名） |
| 日志 | 审计只记元信息（谁/何时/场景/模型/token 数），**不记提示词原文与姓名** |

**层面 2：AI 生成内容标识（法规要求）**

- 现行框架下，**面向内部自用、未向公众提供**的生成式 AI 应用，不适用《生成式人工智能服务管理暂行办法》的主体责任条款（该办法第二条的"教育机构研发、应用……未向境内公众提供服务的，不适用"）；
- 但**内容标识**是低成本高收益的合规动作，且国家正在形成"1+1+N"标识制度体系（另有《人工智能拟人化互动服务管理暂行办法》自 **2026-07-15** 起施行，强调未成年人保护、数据安全）。**建议一律执行**：
  1. 所有 AI 生成的页面/文档显著标注「AI 生成，请核对后使用」；
  2. 导出的 PDF 页脚带生成时间、模型名、生成人；
  3. `ai_generations` 留痕可追溯。
- **未成年人数据**：学生为未成年人，个人信息属敏感；本方案所有措施（不出网、脱敏、本地算指标、权限继承）本质都是为这一条服务的。**这一条不能有例外**。

**层面 3：权限不越界（对应结论 C4）**

在 `ai/` 模块入口做**统一权限闸门**（不分散在各生成器里）：

```
generate(scene, payload, ctx)
  ├─ 1. 校验 ctx.user.role 是否允许该 scene        （教师不能调"教务版销售报告"）
  ├─ 2. 用 utils/scope.js 校验目标学员是否在数据范围内（教师只能查本班）
  ├─ 3. 按 scene 选择指标集（教师版不含金额，教务版含课时数）
  ├─ 4. 走 redact 白名单后出网
  └─ 5. 落 ai_generations（含 scene / operator / 权限上下文快照）
```

### 6.3 可用性与降级

| 场景 | 降级策略 |
| --- | --- |
| 未配置 `LLM_API_KEY` | 走**规则引擎版**（模板 + 本地指标填充），页面明确标识「规则生成（未启用 AI）」。**这个能力必须 Day 1 就有**，否则内网环境无法演示 |
| 调用超时 / 限流 / 服务不可用 | 指数退避重试 1 次 → 失败则降级为规则引擎版，**不阻塞教师主流程**（AI 是增强，不是关键路径） |
| 长耗时任务（整卷生成、批量批改） | 不在请求内同步等待。方案：任务表 + 轮询（`ai_tasks`），或前端流式展示。**推荐先做"任务表 + 前端轮询"**（复用现有 Express，不引入队列中间件）——这符合本项目"零原生依赖"的基调 |
| 生成结果不满意 | 支持"重新生成"（带温度调整）+ 教师可编辑后保存 |

### 6.4 需新增的依赖（尽量少）

| 用途 | 方案 | 依赖增量 |
| --- | --- | --- |
| 调用模型 | `fetch`（Node 24 内置，OpenAI 兼容协议） | **0**（不需要 axios/sdk） |
| PDF 生成（Phase B） | 前端 `window.print()` + `@media print` | **0** |
| PDF 生成（Phase C） | `puppeteer`（或无头 Chromium） | +1 依赖，镜像 +~300MB |
| 文件上传 | `multer` | +1 依赖 |
| 全文检索 | SQLite **FTS5**（`node:sqlite` 是否启用需实测） | 0（若不可用则退化为 LIKE 查询） |
| OCR（Phase C） | 优先用多模态模型直接识图；不满足则接专用 OCR | 待验证 |

**待验证项（开发前必须先跑通）**
- [ ] `node:sqlite` 是否启用 FTS5（`CREATE VIRTUAL TABLE ... USING fts5`）
- [ ] `deepseek-v4-flash` 是否支持图片输入（决定批改作业的实现路径）
- [ ] `node:sqlite` 的 JSON 函数（`json_each`）支持情况（影响 `kp_ids_json` 方案）

## 7. 指标体系（本次功能怎么算成功）

市场同行的数字（"每周省 7–10 小时"）是厂商宣称，**我们不能照抄**。建议用本地可测的指标：

### 7.1 北极星指标
**教师每周因 AI 节省的准备与批改时间（自评 + 使用频次交叉验证）**

### 7.2 驱动指标（AI 使用侧）

| 指标 | 定义 | 目标（上线 8 周后） |
| --- | --- | --- |
| AI 功能周活跃教师数 / 全部教师数 | 至少生成 1 次 | ≥ 60% |
| 教案生成采纳率 | 保存为教案 / 生成总数 | ≥ 50% |
| 试卷审核通过率 | 教师确认可用 / 生成总数 | ≥ 70%（低于此说明出题质量有问题） |
| 学情报告导出数 / 月 | PDF 导出次数 | ≥ 30 份/月 |
| 学情报告被实际使用率 | 有导出记录的学生 / 在读学生 | ≥ 20% |
| AI 结果被修改比例 | 教师编辑过产出 / 生成总数 | 监控项（过低=可能没看就用了，反而危险） |

### 7.3 健康指标（质量与风险）

| 指标 | 定义 | 红线 |
| --- | --- | --- |
| 出网违规次数 | 白名单外字段进入提示词 | **必须为 0** |
| 越权访问次数 | AI 端点返回越权数据 | **必须为 0** |
| 生成失败率 | 调用失败 / 总调用 | < 5% |
| 降级触发率 | 走规则引擎的比例 | 监控项 |
| 教师报错题数 | 教师标记"AI 答案有误" | 每周下降趋势 |

> 特别提醒：**"AI 结果被修改比例"过低是危险信号**，说明教师可能直接采用了未经审核的 AI 产出。这个指标要反向看。

## 9. 风险登记与待拍板问题

### 9.1 风险

| # | 风险 | 影响 | 缓解 |
| --- | --- | --- | --- |
| R1 | **课评成为负担 → 不填 → AI 无燃料**（沿用既有 R1，本次风险更高） | PDF 报告失去意义 | 批量 + 只标异常；与点名流程绑定；每周统计填写率 |
| R2 | AI 生成的题目/答案有错，教师未核对即用 | 教学事故、家长质疑 | 待审状态 + "已核对"勾选才可导出 + 教师报错入口 |

| R7 | 教师不用（"还不如我自己写"） | 投入沉没 | Phase A 先做最高频的备课与学情；小范围试点 2–3 位教师后再全量 |
| R8 | 表单/报告里的销售话术让家长反感 | 口碑损失 | 教务版报告只给 admin；话术由本地模板生成，措辞经校长审核 |
| R9 | 模型能力/价格变化（如 2026-08-17 涨价 200–1100%） | 成本突增 | provider 抽象层可换模型；成本入账可查；默认用 Flash |
