# ADR-008：数据资产化与 AI 产出层架构（系统为唯一数据源）

- **状态**：**已决定**（业务方 2026-09-21 拍板）
- **日期**：2026-09-21
- **决策人**：业务方（机构负责人）
- **相关**：[[ADR-004-AI学情分析采用本地指标加大模型润色]]、[[ADR-007-AI能力采用独立工作台加只读网关与最小权限凭证]]、[[ADR-006-AI学情报告的数据模型与录入粒度]]
- **取代**：本 ADR **部分取代** `ROADMAP.md` §〇 D7 中「不做 RAG 知识库」的结论（见下文「与既有决策的关系」）

## 背景

系统即将在校区正式上线。在上线前的规划讨论中，业务方明确了**长期产品方向**，这超出了 2026-09-12 首次访谈时的设想：

> 「系统是产出一切数据的来源。让老师记录学生学习情况、用 AI 产出成长路径，**这些都是产出，都是在为 AI 后期整合数据做燃料**。最后由 AI 使用不同方式，产生不同结果。未来方向一定是：**所有内容在系统上产生，由 Dify 通过多个工作流产生不同结果。**」

与此前决策相比，新增了三点诉求：

| # | 新诉求 | 与旧决策的差异 |
| --- | --- | --- |
| 1 | 系统要**产出** PPT / PDF / 试卷 / 视频等教学资料 | 旧决策只做到「生成文案」，**没有产出层** |
| 2 | 上课环节产生的**一切数据**都要沉淀，作为 AI 燃料 | 旧决策只沉淀结构化指标 |
| 3 | 要挂**知识库**，让 AI 检索 | **D7 明确写了「不做 RAG 知识库」** |

业务方同时明确表态：

> 「文档的定义是基于当时的生产环境，不代表未来不会改。如果有更好的可能，我为什么不用呢？」

因此在 2026-09-21 的讨论中重新评估了知识库、Dify 定位、文件存储、MCP 等议题，本 ADR 归档结论。

## 决策

### 1. ★ 系统是「唯一数据源」，也是「唯一仓库」

这是本 ADR 的**总纲**，其余各条都是它的推论：

```
老师日常使用 → 数据在系统内自然产生 → 系统沉淀
                                        ↓
                              Dify 读取并加工（只读）
                                        ↓
                              产出结果 → 存回系统
                                        ↓
                              老师使用 → 更多人愿意用 → 数据更多
```

**一句话**：**数据只能存在系统里，Dify 是加工厂，不是仓库。**

### 2. ★★ 数据库存「索引」，文件存「磁盘」（硬性架构）

业务方指出两个问题：① 数据库不能存太重的东西；② 希望归档且能被直接读取。

**决策**：采用业界标准做法 —— **数据库只存元数据，文件本体存磁盘目录。**

| 层 | 存什么 | 说明 |
| --- | --- | --- |
| **数据库（SQLite）** | 业务数据 + **文件索引**（谁、什么类型、路径、生成时间） | 保持轻量，1000 个文件仅数百 KB |
| **磁盘目录** | PPT / PDF / 试卷 / 图片本体 | 放在 `server/data/assets/`，随数据卷一起备份 |

**目录按「人 / 班级 / 教师」组织**，便于人工查找与归档：

```
server/data/assets/
├── students/<学员名>/2026-09-成长路径.pdf
├── classes/<班级名>/2026-09-月考卷.docx
└── teachers/<教师名>/2026-09-月度总结.pptx
```

**理由**：数据库擅长「找关系」，不擅长「存大块字节」；文件放磁盘可被浏览器、Dify、文件管理器**直接读取**，无需「从数据库里取出来」。

### 3. Dify 定位：**加工厂（只读）**，不是知识库仓库

**必须纠正的一个认知**：Dify 的知识库是**只读检索**设计，**不是用来写业务数据的**。

| 环节 | 谁负责 |
| --- | --- |
| ① 取数据 | 系统 → Dify（**脱敏后**） |
| ② 加工 | Dify（检索知识库 + 调 LLM） |
| ③ **存结果** | **存回系统** ← 关键 |
| ④ 展示 | 系统前端（数据来自系统自己的库） |

**为什么不能把结果存 Dify**：Dify 无「按学员 ID 查历史报告」这类接口；`dify/volumes/` 是运行时数据，容器重建可能丢失；向量检索做不到精确查询。

**结论**：AI 生成的任何结果，**必须落回自己的数据库**。

### 4. 知识库分层：业务数据 / 参考资料 / AI 产出，三者分开

| 类型 | 例子 | 存哪 |
| --- | --- | --- |
| **业务数据** | 学员、考勤、成绩、成长记录 | 系统 SQLite |
| **参考资料** | 教学法、话术、SOP、学科知识 | **Dify 知识库（只读）** |
| **AI 产出** | 生成的报告、评语、PPT | **系统**（索引入库 + 文件落盘） |

**判据**：
- 凡是「**某个具体学员 / 班级**」的数据 → **系统**
- 凡是「**通用知识 / 资料**」→ **Dify 知识库**

### 5. Obsidian：定位为「人的资料工作台」，**不作为 AI 知识库**

经评估，Obsidian 存本地 Markdown、无 API、按单人本地设计，**无法作为 AI 的知识来源**。

**结论**：
- ✅ 可作为**业务方自己写教学资料**的工具（若使用）
- ✅ 其产物可**导出 Markdown → 导入 Dify 知识库**
- ❌ **不作为**系统的一部分，**不作为** AI 检索层

**本决策不影响现有 `.obsidian/` 忽略规则**（见 `docs/00-项目导航.md` §六）。

### 6. MCP：不引入（延续既有结论），但澄清「用别人的 MCP」的含义

原结论「MCP 明确不做」**继续有效**，理由：本项目流程**固定且确定**，用 REST 更简单可靠；MCP 适合「AI 自由探索工具」的场景。

**对「使用别人的 MCP」的澄清**：若将来希望外部 AI 助手（如开发期的 AI 编码助手）能**直连查询本系统**，可按 MCP 开放标准把系统**包装成 MCP Server**（无需自行发明协议）。但这属于**开发 / 运维效率工具**，受益者是开发者而非老师，**优先级低于产品功能**。

### 7. 产出层分期：先易后难，禁止一次性全做

| 产物 | 方案 | 阶段 |
| --- | --- | --- |
| **表格 / 数据表** | 已有 `xlsx` 基础 | **第 1 步** |
| **PDF** | 后端渲染 | **第 2 步** |
| **PPT** | `pptxgenjs` 或模板填充 | 第 3 步 |
| **视频** | AI 生成 / 模板合成 | **暂缓**（不可控、成本高、效果不稳） |

**分期原则**：一个小场景验证成功 → 复用经验 → 再推广。**禁止一次性重构架构。**

### 8. 工作流开发顺序：先做「一个样板」，验收后再推广

延续既有约定：**先做 1 个样板场景**（如备课），跑通**三道防线**（脱敏 / 权限 / 降级）并经验收，再决定其余场景是否全迁 Dify。

### 9. 数据采集铁律不变：**永不强制、嵌入既有流程**

虽然要「沉淀一切数据」，但**采集方式不得加重老师负担**：

- **新增表单 = 老师不用**
- 采集入口必须**嵌在已有页面**里
- 分层：第 0 层零操作自动采集 / 第 1 层 10 秒随手记 / 第 2 层 1 分钟打勾

**说明**：数据量再大，**没人录入就是零**。此条是对「沉淀一切数据」诉求的**必要约束**。

## 理由

1. **数据是护城河**：业务联动完整度是本项目相对收费 SaaS 的优势（见 `ROADMAP.md` §一）。让数据在系统内自然沉淀，是长期价值的来源。
2. **文件不入库是行业共识**：数据库存大块二进制会导致体积膨胀、内存压力、查询劣化；索引 + 文件系统是标准解。
3. **Dify 的能力边界要说清**：把它当仓库会导致「数据取不出来 + 丢失 + 查不准」三个问题同时出现。
4. **产出层是独立模块**：与知识库解耦，可分批交付，不必等知识库就绪。
5. **约束先于扩张**：明确「不加重老师负担」，避免为了数据量而毁掉产品可用性。

## 明确不做

- **不做**视频生成（本期；性价比低、不可控）
- **不做**自建 RAG 基础设施（向量库 / embedding pipeline）—— 交由 Dify 承担
- **不做**自行发明 MCP 协议（如需，按开放标准包装）
- **不把** AI 产出直接留在 Dify —— 必须落回系统
- **不改**「纯员工端 CRM」定位：学生 / 家长仍无账号（沿用 ADR-001 / ADR-002）
- **不做** text2sql（沿用 ADR-004）

## 影响

**数据层**
- 需新增「文件资产」表（建议命名 `assets` / `generated_assets`），字段含 `student_id` / `type` / `file_path` / `size` / `created_at`，**只存元数据**
- 需在 `server/data/` 下建立 `assets/` 目录结构（随数据卷备份）
- 需评估磁盘扩容：文本类 32 GB 够用；**若要存视频需扩至 100 GB+**

**产出层**
- 需评估 PDF 渲染方案（后端渲染 vs 前端打印）
- 需评估 PPT 生成方案（`pptxgenjs` 或模板引擎）
- 可复用既有 `xlsx` 经验

**知识层**
- `dify/` 目录从「暂不需要」转为**规划启用**（端口 8081）
- 知识库内容需业务方整理提供（三类来源中的 🟣 知识库）

**文档**
- `ROADMAP.md` §〇 D7 与 §二 Non-goals 需标注本 ADR 的修订
- 新增本 ADR 并登记至 `docs/00-项目导航.md` ADR 索引

## 复审条件

出现以下任一情况时重新评估：

1. **磁盘容量不足**且无法扩容（需改为对象存储 / NAS）
2. **Dify 文档解析能力成为瓶颈**（复杂 PDF / 表格解析不准）→ 评估 RAGFlow 等替代
3. **知识库规模从 10³ 涨到 10⁶ 级** → `node:sqlite` 与 Dify 默认配置均需重新评估
4. **产出物需要批量并发生成**（如全校区一次性生成月考卷）→ 需引入任务队列
5. **业务方决定商业化**（推翻 ADR-001）→ 多租户改造将影响文件存储的隔离策略
