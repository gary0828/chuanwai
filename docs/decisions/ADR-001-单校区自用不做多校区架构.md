# ADR-001：单校区自用，不为多校区预留架构

- **状态**：已接受
- **日期**：2026-09-12
- **决策人**：校长（业务方）
- **相关**：[[ADR-002-家校不做家长端与出网触达]]、[[ROADMAP]]

## 背景

系统下周在校区正式投用。在做功能规划时需要确定服务范围，因为它决定了权限模型、数据模型与报表体系是否需要为"多校区"预留扩展位。

当前规模：**在校学员 200–500 人，员工 5–15 人**。

## 决策

**明确定位为单校区自用系统。不为多校区、租户隔离、跨校区报表做任何架构预留。**

具体排除：
- 校区 / 租户维度与 `campus_id` 字段
- 跨校区数据汇总与对比报表
- 学员跨校区转校、校区间课时转移
- 总部 / 分校两级角色体系

## 理由

1. **规模不需要**：200–500 学员、5–15 员工，单校区完全够用。
2. **预留是有成本的**：多校区不是"加一个字段"那么简单，它会渗透到每张表的查询条件、每个接口的权限过滤、每张报表的聚合维度。为一个不确定的未来付确定的复杂度成本，不划算。
3. **预留 ≠ 便宜**：真要开分店时，SQLite 单库 + 单机部署大概率也要重做，预留省不下多少。

## 影响

- 所有表保持单一 id 主键，不加校区维度
- 权限模型维持 `admin` / `teacher` 两角色
- 报表只做全校口径，不做分校区下钻

## 复审条件

出现以下任一情况时，本决策需重新评估：
- 确定开设第二个校区
- 学员规模超过 1000 人（很多"单校区"假设会失效）

## 例外

无。
