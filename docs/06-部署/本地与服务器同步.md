# 本地与服务器同步

> 原则（用户 2026-09-23 拍板）：**服务器用什么版本，本地就用什么版本** ——
> 同一份编排、同一端口、同一份代码，**数据也保持一致**。

---

## 1. 三条铁律

| # | 铁律 | 为什么 |
|---|---|---|
| 1 | **只有一份编排**：`docker-compose.yml`（统一入口单端口 18080） | 多形态必然脱同步（上传 413、跳转串端口都栽在这） |
| 2 | **同目录 `git pull`，绝不另开新目录 clone** | 数据在 `server/data/`（bind mount）；新目录没数据 → 首启自动建库并灌**种子演示数据** |
| 3 | **服务器是权威数据源** | 本地数据由服务器快照还原；反向同步仅在特殊场景做，且必须先备份 |

---

## 2. 代码同步（两端同版本）

**服务器端（权威）**

```bash
cd <项目目录>
bash server/scripts/backup-db.sh                    # ① 永远先备份
git pull                                            # ② 拉新代码
docker rm -f attendance-server attendance-unified attendance-web attendance-ai-workbench 2>/dev/null || true
docker compose up -d --build                        # ③ 重建统一入口
```

**本地**

```bash
git pull                                            # 与服务器同一 commit
docker build -t attendance-system-server  -f server/Dockerfile .
docker build -t attendance-system-unified -f deploy/Dockerfile.unified .
docker compose up -d --no-build                     # 中文目录不能走 compose --build，见 §4
```

> 校验两端同版本：`git rev-parse HEAD` 与服务器一致（或在同一个 tag/commit 上）。

## 3. 数据同步（本地 ← 服务器）

### 3.1 为什么不能只拷 `attendance.db`

SQLite 运行在 **WAL 模式**：除了 `attendance.db` 还有 `attendance.db-wal`（未合并的事务页）。
**只拷 db 文件 → 拷出来是损坏的**（启动报 `database disk image is malformed`）。
必须用 `VACUUM INTO` 产出**自包含单文件快照**。

### 3.2 标准流程（服务器 → 本地）

```bash
# ① 服务器上：不停机热备（VACUUM INTO，快照一致）
bash server/scripts/backup-db.sh
# 产物：server/data/attendance-<时间戳>.db

# ② 拷到本地（scp / rsync / U 盘）
rsync -aP <user>@<服务器>:/opt/jx-system/server/data/attendance-<时间戳>.db ./server/data/
# ★ 上传资产（Logo / 图标）一起同步，否则本地裂图
rsync -aP <user>@<服务器>:/opt/jx-system/server/data/assets/ ./server/data/assets/

# ③ 本地：停后端 → 用快照还原 → 起容器
docker compose stop server
bash server/scripts/restore-db.sh server/data/attendance-<时间戳>.db attendance-server -y
docker compose up -d --no-build
```

### 3.3 还原后必做

- **重启一次 server 容器**（Windows bind mount 有缓存，否则可能读到旧数据）
- 登录核对：**学员数 / 班级数 / 最近考勤** 是否与服务器一致
- `curl http://127.0.0.1:18080/api/health`

### 3.4 反向（本地 → 服务器）

**默认不做**：服务器是权威，本地多为演示/测试库。确需时（如本地造的数据要上线）：
本地 `backup-db.sh` 出快照 → **先在服务器备份** → 再 `restore-db.sh`。

### 3.5 数据安全红线

- 本地会存有**真实学员/家长数据** → 属敏感数据：不进任何 git 提交、不外传
- `server/data/` 已由 `.gitignore` 排除；提交前仍应扫一遍敏感数据
- 本地快照用完即清理，不要无限堆积

## 4. 本地已知坑：中文目录

`docker compose up --build` 在中文路径下**必然失败**（Docker Desktop / Buildx 的 gRPC 缺陷：
构建时把工作目录写进 gRPC 头，非 ASCII 直接报 `failed to dial gRPC`）。

**必须两步走**：

```bash
docker build -t attendance-system-server  -f server/Dockerfile .
docker build -t attendance-system-unified -f deploy/Dockerfile.unified .
docker compose up -d --no-build
```

> 最省事的根治办法：**把项目放在纯 ASCII 路径**（如 `D:\jx-system\`）。

### 4.2 非登录 shell 的 PATH 陷阱（Windows）

`bash server/scripts/docker-verify.sh` 属于**非登录 shell**，**不会加载 `/etc/profile`**，
于是 Git Bash 下 `/usr/bin` 可能不在 PATH → `grep/sed/wc/cut/tr/tail` 全部 `command not found`
→ **断言无法求值，接口明明返回 200 且 JSON 正确，却被误报 FAIL**（2026-09-23 实测：9 项里 6 项假失败）。

`docker-verify.sh` / `backup-db.sh` / `restore-db.sh` 已在 `set -euo pipefail` 后统一自愈：

```bash
PATH="/usr/bin:/bin:$PATH"
```

Linux 上这两个目录本就存在、无副作用。**你新写的脚本若要在本机跑，请照抄这一行。**

> 交互式 Git Bash（正常打开终端）不受影响；只在被 CI / 定时任务 / 别的工具以
> `bash xxx.sh` 方式调用时才会踩到。

## 5. 本地开发（不跑 docker 时）

| 端 | 命令 | 端口 |
|---|---|---|
| 后端 | `cd server && npm run dev` | 3000 |
| 前端 | `pnpm dev`（已代理 `/api` → 3000） | 8848 |

> ⚠ 统一入口**不对外暴露 3000**（服务器同样如此）。所以 dev 模式下后端要**本地起**，
> 不能指望 docker 容器给 3000 —— 这是"与服务器一致"的必然结果。

## 6. 每次同步后的验收清单

- [ ] `git rev-parse HEAD` 两端一致
- [ ] `curl http://127.0.0.1:18080/api/health` → ok
- [ ] `/` 200、`/ai/` 200、`/api/health` 经 nginx 反代 200
- [ ] 登录后 **学员数 / 班级数 / 最近考勤** 与服务器一致
- [ ] `bash server/scripts/docker-verify.sh`（9 项）
- [ ] 改过路由 / 菜单 → 跑全页面冷启动巡检（28 项）
