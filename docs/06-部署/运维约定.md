# 部署与 nginx

> 目的：改任何部署 / nginx 配置前必读。**这里每条都对应一次真实事故。**

---

## 1. ★ 只有一份 nginx（2026-09-23 起）

| 文件 | 用途 |
|---|---|
| `deploy/nginx-unified.conf` | **唯一** nginx 配置 —— 统一入口（教务 `/` ＋ 工作台 `/ai/` ＋ 后端 `/api`），由 `docker-compose.yml` 的 `unified` 服务使用 |

> 原「三端口」形态的根 `nginx.conf`、以及「工作台单独部署」用的 `ai-workbench/nginx.conf`
> 已随统一编排**一并废弃删除** —— 「多份 nginx 脱同步」这一类问题从设计上消失。

**历史教训（保留备查）**：曾经三份 nginx 必须手工同步，漏改一份该形态就坏 ——
① `client_max_body_size` → 上传 413；② `/assets/` 反代 → 图片 404。如今只剩一份，不会再发生。

## 2. ★ `/assets/` 前缀陷阱（2026-09-21 事故；「工作台自托管」时代）

> **历史事故（该 nginx 现已删除，原理仍适用）**：工作台曾由自己的 nginx 托管
> （`ai-workbench/nginx.conf`，已随统一编排废弃）。当时在那里反代后端资产的 location
> **必须收窄到 `/assets/site/`**，写成 `/assets/` 会让工作台整页白屏：
>
> ```nginx
> location ^~ /assets/site/ { proxy_pass http://server:3000; }   # ✅
> location ^~ /assets/      { proxy_pass http://server:3000; }   # ❌ 工作台整页白屏
> ```
>
> 现在的统一入口（`deploy/nginx-unified.conf`）已按正确方式组织；**改动它时下面这条原理依然适用**。

原因：**两端产物路径不一样** ——

| 端 | 构建产物位置 |
|---|---|
| 教务端 | `/static/js/index-*.js` ← 写 `/assets/` 没事 |
| **工作台** | **`/assets/` 顶层**（`/assets/index-*.js`）← 写 `/assets/` 会**死** |

- ★★ **症状诊断口诀：`/` 返回 200 但页面空白 = 静态资源（JS/CSS）404。**
  **"根路径 200"不能证明前端正常**，必须单独验入口 JS。
- 后端资产目录约定 `server/data/assets/<kind>/`（ADR-008）；
  **新增 kind 时要在这里补一条**。
- `deploy/nginx-unified.conf` **不受影响**（工作台挂 `/ai/assets/`，且正则嵌在 `/ai/` 内部）。
- `^~` 是必需的：否则会被下面 `\.(js|css|png|...)$` 正则抢走（**正则 location 优先级高于普通前缀 location**），
  去本地 docroot 找 → 404。

## 3. ★ `client_max_body_size` 忘了配 = 上传 413

nginx 默认仅 **1MB**，超了在 nginx 层就被拒，**请求到不了后端**。

- **判据（最快的定位法）**：同一文件经 nginx **413**、直连 `:3000` 却 **200** → **100% 是 nginx 层**
- **nginx 层的失败不进后端日志** —— 别一头扎进后端代码
- 体积三层上限必须对齐：**前端 2MB → nginx 20m → 后端 2MB**（以后端为准），超限返回 **413**（不是 400）+ 中文提示

## 4. 形态与端口

**2026-09-23 起只有一种形态**（原「三端口」形态已删除，开发与部署共用同一条编排）：

| 形态 | 说明 |
|---|---|
| **统一入口**（唯一） | 一个 nginx 托管教务 `/` + 工作台 `/ai/` + 反代 `/api`，**对外只开 1 个端口** → `docker-compose.yml`（`docker compose up -d`） |

- 8081 已被 Dify 占用；**对外无域名请用 18080**；**5180 属 Windows 保留端口段**
- 后端容器名固定 `attendance-server`；统一入口容器名 `attendance-unified`

## 5. ★ 跳转要"跟随访问者"

`AI_WORKBENCH_URL` 配**回环地址**时，后端 `resolveWorkbenchUrl()` 会换成访问者的地址
—— 这是「AI 工作台点击进不去」的根治方案。

**跟随粒度取决于形态 —— 换的只是 hostname，不是整个 origin：**

| 形态 | 配置 | 规则 |
|---|---|---|
| A 工作台在**另一台机器 / 另一端口** | `URL=...:8082`、`AI_WORKBENCH_BASE_PATH` **空** | 只换 hostname，**保留配置的端口与协议** |
| B 统一入口（本项目默认且唯一） | `URL=http://localhost`、`BASE_PATH=/ai` | 跟随**完整 origin**，再补 `/ai` |

判据：**`AI_WORKBENCH_BASE_PATH` 非空即同源部署。** 形态 A 误用完整 origin → 落到教务系统（无 `/sso`）→ **404**。

## 6. ★ 重建 server 后必须 reload 统一入口 nginx

`docker restart attendance-server` 之后，要 `docker exec attendance-unified nginx -s reload`
—— 否则 nginx 里缓存的旧 upstream 解析会导致 502。
（2026-09-23 前该容器名为 `attendance-web`（三端口形态），已随统一编排删除。）
