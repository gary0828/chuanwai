## 一、分项结论

### 2.1 代码结构与组织 —— 82 分（良好）

**结论：结构健康，可维护性达标，无须大规模重构。**

- 后端 22 个路由文件按业务域切分，`utils/{audit,backup,scope}.js` 职责单一；`middleware/auth.js:50-58` 提供 `requireRole` 统一角色守卫，语义清晰。
- 前端 `src/views` 按 `attendance / finance / teaching / system / recruit / family` 六大域组织，32 个 `.vue` 无错位。
- **接口层收口良好**：`grep -rE "['\"\`]/api" src/views src/store src/layout` 零命中，所有请求集中在 `src/api/{user,routes,teaching,attendance}.ts`，符合项目既有约定。

**待改进**：
- 32 个列表页各自实现 `searchForm + pagination + loadData + el-table` 四件套，无公共 composable → 一处交互改版需改 32 处（低）。
- 2 个超大组件：`src/views/finance/orders/index.vue`（909 行）、`src/views/attendance/statistics/index.vue`（823 行）（低）。
- `src/views` 内 149 处 `.then(` 对 32 处 `.catch(`，其中 25 处为 `catch(() => {})` 空吞（中，见 M13）。

### 2.2 核心业务逻辑正确性与清晰度 —— 62 分（存在必修断裂）

**结论：P0 主链路（签到 / 学生 / 成绩 / 销售）可跑通，但两条业务闭环存在缺口，均与"建档即生效"的隐含假设有关。**

**✅ 已核实的亮点**：课时扣减/回补逻辑设计合理且有注释说明版本演进（`attendance.js:76-90`，v13 引入"优先扣剩余课时最多的订单"+"回补不设余额门槛"）；退费审批有状态机保护（`finance.js:362-365` 拒绝非"待审批"与非"在读"订单重复通过）。

**❌ 业务闭环断裂**：

1. **招生线索一键转化 → 课时包缺失（阻断 B2）**
   `leads.js:296-313` 的 `INSERT INTO orders` **不含 `total_hours` 字段**，落库即为默认值 0。而：
   - `attendance.js:81` `findDeductOrder` 要求 `total_hours > 0` → 转化来的学员考勤**永不扣课时**；
   - `finance.js:638` `revenue_recognized` 要求 `o.total_hours > 0` → 该订单**永不确认收入**。
   同时 `docs/api.md:308-320` 明确宣称 convert 支持 `total_hours` 参数，前端若按文档接入，参数会被静默忽略。
   → **需业务确认**：若"转化仅建档、报班在财务补录"是设计意图，则必须修正 `docs/api.md`；若否，则必须补写 `total_hours`。**两种情形都必须在上线前落地其中一种**，否则招生链路产出的是"零课时学员"。

2. **请假销假回补口径与考勤回补不一致（高 H10）**
   - 考勤回补 `attendance.js:84` `findRefundOrder`：`student_id + course_id + status='在读' + total_hours>0`（**无** `remain_hours>0`，注释明确"余额为 0 时同样可以回补恢复"）。
   - 请假回补 `leaves.js:138` `findOrder`：同上**但多一个 `remain_hours > 0`**。
   触发条件并非边缘场景：**每个学员都会经过"剩余课时 = 1"这一天**。此时缺勤扣减 → `remain_hours` 归 0 → 销假审批时 `findOrder` 查不到订单 → 该课时**永久不回补**，且不写 `hour_consumptions` 回补流水，账实不符。
   → 修复：将 `leaves.js:138` 的条件与 `attendance.js:84` 对齐（删去 `remain_hours > 0`）。

**✅ 已核实无问题**：`students` 表**并不存在** `total_hours / remaining_hours / balance` 字段（全库 grep 仅命中文档），课时冗余实际落在 `orders.total_hours/remain_hours`，因此不存在"缴费后 students 余额未同步"的问题；`classes.student_count` 为实时子查询而非存储列；`schedules.attended_count` 不存在。

### 2.4 潜在缺陷与异常处理 —— 70 分

**✅ 已核实**：统一错误中间件在位（`index.js:107-110`）；启动期迁移失败即抛错终止（`db.js:17`）；错误响应不泄露堆栈（合规）。

**❌ 缺陷**：
- **前端 token 刷新会永久挂起请求（高 H1）**：`src/utils/http/index.ts:86-96` 的刷新链路为 `.then().finally()`，**无 `.catch()`**。刷新失败时 `PureHttp.requests` 队列中的回调永不被调用，`retryOriginalRequest`（`:50-57`）的 Promise 永不 resolve → 相关请求永久 pending，同时产生 unhandled rejection。叠加响应拦截器（`:133-138`）**无 401 → 跳登录**逻辑，token 真失效时用户看到的是"界面卡死"而非"重新登录"。这是上线后最可能被用户感知的缺陷。
- **全局错误中间件忽略 `err.status`**（`index.js:107-110`）：`utils/backup.js:62/67/80/87` 抛出的 400/404 一律被转成 500，前端无法区分"参数错"与"服务错"（中 M4）。
- **无异步兜底**：`index.js` 未注册 `process.on('unhandledRejection' / 'uncaughtException')`。当前路由全为同步 handler（grep 无 `async (req`），缺口暂不触发，但一旦引入 async handler 即成真实风险（中 M5）。
- **验证码形同虚设**：`src/views/login/index.vue` 有图形验证码，后端 `auth.js:403 /login` **完全不校验** → 直接调 API 即可绕过；叠加无限流（H7）与默认弱口令（H9），登录接口可被自动化爆破（中 M9）。

### 2.5 性能瓶颈 —— 74 分

**结论：按当前规模（学员 200–500 / 员工 5–15）不构成阻塞；问题集中在批量写入与缺失索引，属"现在修成本极低、以后修成本极高"的类型。**

**N+1 / O(N) 写入（中）**：
- `attendance.js:137-213` 批量考勤：per-record 执行 8–10 次查询，一个 30 人班级 ≈ 300 次查询。
- `students.js:184-240` Excel 导入：**无行数上限**，每行一个独立事务（`canManageClass` 1 次查询 + 独立 `BEGIN/COMMIT`）→ N 行 N 事务，既慢又丧失整体回滚语义（高 H13）。
- `exams.js:287-299`、`leaves.js:183-200` 同类模式；`dashboard.js:63-86` 在循环内重复 `db.prepare()`（应移出循环）。

**缺索引清单（高 H11）**——对照 `server/src/migrations/*.js` 实际 DDL：

| 高频查询路径 | 位置 | 缺失索引 | 说明 |
