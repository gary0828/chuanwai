# ADR-009：课次实体与课消归属（教学事件的唯一枢纽）

- **状态**：**已决定**（业务方 2026-09-23 拍板）
- **日期**：2026-09-23
- **决策人**：业务方（机构负责人）
- **相关**：[[ADR-008-数据资产化与AI产出层架构]]、[[ADR-001-单校区自用不做多校区架构]]、[[ADR-005-课堂评价采用全班默认良好只标异常]]
- **前置**：本 ADR 是排课治理（F4 代课 / F5 停课 / F6 教室冲突 / F7 批量排课）与作业模块（ADR-012 §5）的**共同前置**

## 背景

### 现状：只有「排课模板」，没有「课次实例」

| 表 | 结构 | 性质 |
| --- | --- | --- |
| `schedules`（v4） | `class_id × day_of_week × period` | **周循环模板**，无日期区间、无教室、无教师、无课次 |

而所有"按课次"的业务，**都在用日期字符串近似课次**：

| 业务 | 现在挂在哪 | 问题 |
| --- | --- | --- |
| 考勤 | `attendances.date` | 无法回答"这是第几次课" |
| 课时消耗 | `hour_consumptions.date` + `class_id` | **无法精确对账到某一节课** |
| 课堂评价 | `class_evaluations.eval_date` | 课次序号只能靠日期猜 |
| 补课 | `makeup_classes.original_date` / `makeup_date` | 靠日期字符串关联，改名/调课即断 |
| 调课 | `schedule_adjustments.from/to_day_of_week` | 只有"星期几+节次"，**没有具体日期** |

### 后果（五条，都不是"少个页面"）

1. **教室冲突检测没有载体** —— 冲突发生在"某一天某一节"，而模板里没有"这一天"
2. **代课没有载体** —— "3 月 5 日第 3 节换张老师上"无处存
3. **停课（节假日）只能靠调课记录打补丁**
4. **教学进度无从谈** —— "这节课该讲什么 / 实际讲到哪"无处存
5. **课次级统计口径会漂** —— 一切都要靠 `date` 反推

### 两个独立来源给出同一结论

| 来源 | 主张 |
| --- | --- |
| 本项目《教务功能补全分析》S1（2026-09-23） | 缺「课次实例」，是排课体系的天花板 |
| 外部《全学段教务管理平台 PRD》§6.4 + §20 决策2 | 「**每一节课生成唯一 `lesson_instance_id`，作为签到、课消、作业、课堂记录等数据的连接键**」 |

> 外部 PRD 由他人独立撰写，未参考本项目 → **同一结论被独立复现两次**，故本 ADR 直接立项。

## 决策

### 1. ★★ 新增 `class_sessions`（课次实例）—— 一节真实发生的课

**核心原则**：**模板描述"通常"，课次描述"这一次"**。两者分离，模板不被破坏。

| 字段 | 说明 |
| --- | --- |
| `id` | 课次 ID（全系统的教学事件连接键） |
| `schedule_id` | 来源模板（可空；手工加课/补课为空） |
| `class_id` / `course_id` | 班级 / 课程 |
| `teacher_id` | **本节课的授课教师**（可因代课而与模板不同） |
| `room_id` | 教室（可空；教室资源见 F6） |
| `session_date` | **具体日期**（模板里没有的那一维） |
| `period` | 节次 |
| `start_time` / `end_time` | 起止时间（用于时长与冲突判断） |
| `status` | `待上课` / `已上课` / `已停课` / `已调课` / `已取消` |
| `topic` | 本次教学主题（承接"教学大纲与进度"） |
| `origin` | `模板生成` / `调课` / `补课` / `手工` |

**唯一约束**：`(class_id, session_date, period)`

### 2. 四张既有表挂上课次（+ 作业表新挂）

| 表 | 新增 | 迁移处理 |
| --- | --- | --- |
| `attendances` | `session_id` | 按 `(class_id, date, 节次)` 反查回填；回填不上的置空并记入异常清单 |
| `hour_consumptions` | `session_id` | 同上（**课消精确对账的关键**） |
| `class_evaluations` | `session_id` | `session_no` 由课次推算，不再手填 |
| `makeup_classes` | `original_session_id` / `makeup_session_id` | 由日期字符串改为课次引用 |
| `assignments`（ADR-012 §5） | `session_id` | 新建表时直接带上 |

### 3. 课次是「唯一教学事件枢纽」

教室冲突 · 代课 · 停课 · 课消 · 课评 · 作业 · 教学进度 —— **全部以 `class_sessions.id` 为准**，不再各自用日期近似。

### 4. 生成方式：**由模板批量生成实例**，而非实时推算

按学期范围（`terms`）一次性生成整学期课次，之后**逐次修改实例**（停课改状态、代课改 `teacher_id`、调课改 `session_date`）。

**为什么必须"实例化"而不是"实时按模板算"**：
- 只有实例才能被**单独修改**（"下周三那节课停掉"不能影响其他周三）
- 只有实例才有**稳定 ID**，供考勤/课消/作业/课评引用
- 实时推算会让"改了模板 → 历史数据全部错位" —— **历史不可篡改**（延续 ADR-008 §9 与 v18 时间轴「只增不改」原则）

### 5. `schedules` 语义不变，降级为「排课模板」

不改字段、不清数据。课次由它生成，**模板与实例并存**。

## 理由

1. **上游阻断已确认**：F4/F5/F6/F7 与作业模块都卡在同一块地基上。按 `ROADMAP.md` §4「排序例外：标注为前置依赖的项不参与 RICE 排序，按依赖顺序强制前置」——本项必须**先于**它们立项。
2. **不改会持续产生补丁**：每加一个"按课次"的功能，就要再发明一次日期近似；补丁之间互不认识。
3. **课消对账是钱**：`hour_consumptions` 现在挂不到具体课次，与家长对账时只能"按日期大致对"，这是收入口径的隐患（与 ADR-003 同源）。
4. **实例化是唯一可审计方案**：可追溯（谁在何时改了哪一节课）与不可篡改，都要求实例 + 稳定 ID。
5. **成本可控**：模板 → 实例是一次批量生成，不是实时计算；学期级操作，频次低。

## 明确不做

- **不做**教室自动分配算法（人工指定 + **冲突检测**即可；自动排课是另一个量级的工程）
- **不做**走班排课（单校区培训机构无此场景）
- **不做**在线课 / 直播课 / 录播
- **不做**把 `schedules` 改造成实例表（**两者语义不同，必须分开**）
- **不改** ADR-001「单校区自用」

## 复审条件

1. **回填失败率过高**（历史数据无法可靠映射到课次）→ 需评估"只对新学期启用课次 + 历史保持日期近似"的分段方案
2. **学期级课次生成量超出预期**（如 200+ 班 × 40 周 × 每周 3 节 = 24000 行）→ 评估分区或按需生成
3. **出现走班 / 线上课需求**（本 ADR 已排除）→ 重新评估
4. **教室资源不足**成为主要矛盾 → 提前启动 F6（教室与三重冲突）
