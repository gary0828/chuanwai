# ADR-010：学员生命周期状态机（两层状态，不合并）

- **状态**：**已决定**（业务方 2026-09-23 拍板）
- **日期**：2026-09-23
- **决策人**：业务方（机构负责人）
- **相关**：[[ADR-003-财务只做学员账户与剩余学费口径]]、[[ADR-009-课次实体与课消归属]]、[[ADR-012-商用化定位与边界修订]]
- **取代**：本 ADR **取代**《教务功能补全分析 v1》S3 中「建议把两个状态字段合并为一处」的**初步建议**（该建议经复审后**不成立**，见下文「背景 · 为什么不能简单合并」）

## 背景

### 现状：两个状态字段，一层语义被混淆

| 表 | 字段 | 取值 | 实际语义 |
| --- | --- | --- | --- |
| `students` | `status` | `在读` / `休学` / `退学` | **学员与机构的学籍关系** |
| `orders` | `status` | `在读` / `结业` / `退班` | **单个课程包（报班）的进行状态** |

**症状**：同一个学员"是否还在读"有两个答案；且 **`students` 里根本没有"结业"** —— 一个学完课程的孩子，在学员档案上仍然是"在读"。

### 为什么不能简单合并（对 v1 初步建议的复审）

v1 曾建议"统一到一个状态字段"。**复审后判定不成立**，理由：

1. **这两层状态是真实存在的两个概念，且可以同时不同**：
   一个学员可以"课程包 A 已结业、课程包 B 仍在读" —— **合并即丢信息**。
2. **合并会让"在读/结业"这类词在两个层级间打架**：同一词汇表达两件事，是口径混乱的根源，而不是解法。
3. 外部《全学段教务平台 PRD》§5.1 给的是**学员级**状态机（潜在线索→试听中→在读→暂停→毕业/结业→流失/终止→归档），**没有订单级概念** —— 照搬会把"报班"这一层抹掉。

> **结论**：正确解法不是"合并"，而是 **分开两层 + 把口径与联动规则写死**。

## 决策

### 1. ★ 明确两层状态，各自单一职责

| 层 | 字段 | 回答的问题 | 取值（定格） |
| --- | --- | --- | --- |
| **学员层** | `students.lifecycle_status`（由 `status` 更名，**语义显式化**） | 这个学员**与机构的关系**是什么？ | `在读` / `暂停` / `结业` / `流失` / `归档` |
| **报班层** | `orders.status`（**保持不变**） | 这一个**课程包**进行到哪了？ | `在读` / `结业` / `退班` |

### 2. 学员层状态定义与允许操作

| 状态 | 定义 | 何时进入 | 允许操作 |
| --- | --- | --- | --- |
| **在读** | 至少有一个课程包处于 `在读` | 报名建档 / 报班 | 排课、考勤、请假、评价、续报 |
| **暂停** | 暂时停止学习，但保留学籍（原"休学"） | **人工**（家长申请 + admin 操作） | 恢复（→ 在读）、转班、结班 |
| **结业** | **全部**课程包均为 `结业`，且学员已完成当前学习阶段 | **自动候选 + 人工确认**（见 §3） | 查看历史、生成结课报告、续报/升班 |
| **流失** | 服务关系终止（原"退学"/"退班"合并语义） | 人工（退班且不再续报） | 保留历史、记录流失原因（用于归因分析） |
| **归档** | 长期保存的历史状态 | 人工（结业或流失 N 个月后） | 仅授权人员访问、列表默认不显示 |

> ★ **术语统一**：原 `休学` → **`暂停`**；原 `退学` → **`流失`**。"退班"是**订单层**的概念，不再出现在学员层。

### 3. ★ 联动规则（写死，避免两处口径漂移）

```
学员层 = 结业   当且仅当   该学员的全部订单.status 均为 '结业'
学员层 = 在读   当且仅当   至少一个订单.status = '在读'
学员层 = 流失   当且仅当   （无在职订单）且（非结业）且（人工确认不再续报）
```

- **自动部分**：有订单状态变化时，后端重算"结业候选"
- **人工确认部分**：`结业` **必须由 admin 确认**才落状态并触发结课流程（ADR-012 §7）
  —— 理由：结业 = 进入续报流程，是**商业动作**，不能由一条 SQL 自动决定
- **冲突处理**：人工设置优先级高于自动重算；人工设置后，自动重算**不得覆盖**（需记入修正留痕，见 ADR-011）

### 4. 状态变更必须留痕

每一次状态流转记录：`原状态 / 新状态 / 原因 / 操作人 / 时间`，走 **ADR-011 的修正留痕机制**。

**理由**：流失原因分析是续报改进的**唯一输入**；无原因的流失记录等于没有。

### 5. `leads`（招生线索）**不并入**本状态机

线索（`leads`）与学员（`students`）是**两个实体**：线索转入系统后**建档为学员**，此后生命周期归本 ADR 管辖。

> ⚠️ 外部 PRD §5.1 把"潜在线索 / 试听中"放进**同一张**学生状态表 —— **本 ADR 明确不采纳**：
> 线索没有学籍，把它塞进学员状态机会导致 `students` 表出现大量无班级、无订单的空壳记录。

## 理由

1. **两层概念客观存在**，合并会造成信息丢失（一个学员多课程包是培训机构的常态）。
2. **口径显式化**是本项目反复踩坑后的共识（见 `ROADMAP.md` R7「剩余学费口径争议」）—— 同类风险不应在状态字段上重演。
3. **`students` 缺"结业"是硬伤**：它直接卡住结课评定与续报流程（ADR-012 §7），必须补。
4. **"结业"必须人工确认**：它触发商业动作（续报），且涉及成绩/出勤/课时的综合判定，不适合纯自动。
5. **流失原因留痕**：没有原因统计，续报改进无从下手 —— 这是最容易被省掉、却最有长期价值的一条。

## 明确不做

- **不做**把两层状态合并为一张表 / 一个字段
- **不做**把 `leads` 线索状态并入学员状态机
- **不做**学员自助改状态（沿用 ADR-002：学员无账号）
- **不做**自动"流失"判定（连续缺勤只进待办预警，**不自动改状态**）

## 影响

**数据层**
- `students.status` → 更名并**扩展 CHECK**（`在读` / `暂停` / `结业` / `流失` / `归档`）
- ⚠️ SQLite 无法直接改 CHECK → **必须重建表**（沿用 v2/v10/v14 的重建模式）
- 数据迁移映射：`休学` → `暂停`、`退学` → `流失`；**`结业` 需按 §3 规则回算**

- 新增迁移脚本（版本号连续，当前基线 **v20**）+ 同步 `server/database.md`

**接口 / 前端**
- 学员列表增加"生命周期状态"筛选；学员 360 显示**状态流转时间线**
- 前端状态枚举与文案统一（`休学` / `退学` 字样需全量替换）
- ⚠️ **横向同类扫描**：`休学`/`退学` 在前后端、字典常量、导出表头、报表口径中的出现位置需**一次扫全**（沿用本项目"只改一处"的事故教训）

**文档**

## 复审条件

1. **出现跨学段升学**（小学→初中）且需要连续档案 → 需评估"学段经历"独立成表（ADR-012 §6）
2. **"暂停"使用率极低**且语义与"流失"混淆 → 评估合并
3. **需要按学员层状态驱动财务口径**（如"暂停不计预收账款"）→ 需回到 ADR-003 联动修订
4. **归档策略需要自动执行**（按时间自动归档）→ 评估定时任务
