# ADR-011：数据修正留痕与对外可信数据

- **状态**：**已决定**（业务方 2026-09-23 拍板）
- **日期**：2026-09-23
- **决策人**：业务方（机构负责人）
- **相关**：[[ADR-003-财务只做学员账户与剩余学费口径]]、[[ADR-009-课次实体与课消归属]]、[[ADR-010-学员生命周期状态机]]、[[ADR-012-商用化定位与边界修订]]
- **前置**：作业模块（ADR-012 §5）的登记数据**同样受本 ADR 约束**

## 背景

### 现状：有"操作日志"，没有"数据修正记录"

| 现状 | 事实 |
| --- | --- |
| `audit_logs`（v7） | 记录**谁在何时调了哪个接口**（操作维度），**不记录"哪个字段的原值被改成了什么"**（数据维度） |
| `exam_scores`（v11） | 只有 `created_at`，**连 `updated_at` 都没有** —— 一个成绩被改过几次、改前是多少，**系统完全不知道** |
| 修改入口 | 批量录分采用"UNIQUE(exam_id, student_id) + 冲突覆盖"（v11 注释原文）→ **覆盖即无痕** |

### 为什么这是硬伤

1. **成绩是对外可信度最高的数据**：家长质疑"我孩子明明是 90 分"时，系统拿不出证据链。
2. **它已经进入看板与下游计算**：成绩趋势、班级分析、成长档案、学情报告都建立在成绩之上 —— 源数据不可信，上层全是错的。
3. **"改过"这件事本身就是信息**：一门课成绩被反复修改与从未被修改，含义完全不同。
4. **两个独立来源同结论**：本项目《教务功能补全分析》（成绩修改留痕）与外部《全学段 PRD》§8.2「必须保留 **原值—新值—原因—操作者—审批人—时间—来源**，**禁止直接覆盖后无痕**」指向同一要求。
5. **作业登记加剧了这个问题**：ADR-012 §5 的作业完成率将进入校长看板并影响教师考核 —— **不能无痕改**。

## 决策

### 1. ★★ 新增通用「数据修正记录」表（`data_change_logs`）

**一次设计，多处复用** —— 不是给每个模块各写一套留痕。

| 字段 | 说明 |
| --- | --- |
| `id` | — |
| `table_name` | 被改的表（如 `exam_scores`） |
| `record_id` | 被改的行 ID |
| `field` | 被改的**字段名**（字段级，不是行级） |
| `old_value` / `new_value` | **原值 / 新值** |
| `reason` | **修改原因**（关键字段必填） |
| `operator_id` | **操作者** |
| `operator_role` | 操作者角色（留档，防角色变更后失真） |
| `approver_id` / `approved_at` | **审批人 / 审批时间**（需审批的场景必填） |
| `source` | 来源：`web` / `import` / `api` / `auto` |
| `occurred_at` | 发生时间 |

### 2. ★ 记录方式：由**后端统一写**，不由各路由自己写

**理由**（本项目真实事故）：`H6` 曾判定"审计覆盖不完整"，核查后发现真实问题是 **5 个模块各自重复写审计** → 最终用**全局中间件 + 白名单**收口。
**本 ADR 沿用同一教训**：留痕逻辑集中在数据访问层（或中间件），**禁止每个业务路由各写一份**。

### 3. 适用范围（第一批白名单，按优先级）

| 优先级 | 表 | 字段 | 是否需审批 |
| --- | --- | --- | --- |
| **P0** | `exam_scores` | `score` | **是**（admin 审批） |
| **P0** | `hour_consumptions` / `orders` | 金额、课时数、`remain_hours` | **是**（admin 审批） |
| **P0** | `assignment_submissions`（新） | `status` / `is_late` / `quality` | 否（只留痕） |
| **P1** | `students` | `lifecycle_status`（ADR-010）、监护人、手机号、证件类 | 状态流转留痕；**关键字段需审批** |
| **P2** | `attendances` | `status` | 否（但补签需走审批，见 `ROADMAP.md` P1） |

> ★ **白名单是刻意的**：不做"全表全字段通用审计"（那是过度设计，且会淹没真正重要的记录）。

### 4. ★ "不可见即不可信"：修正记录必须**可见**

- 成绩详情 / 学员 360 / 课消流水：提供**「修改记录」入口**（展示原值—新值—原因—人—时间）
- 让"改过"这件事**被看见**，而不是藏在数据库里 —— **这是留痕能起作用的前提**

### 5. 不可修改性：修正记录**只增不改**

一旦写入，不允许 UPDATE / DELETE（与 `student_timeline`（v18）「只增不改」同一原则）。

## 理由

1. **可信度是商用交付的底线**：商用定位（ADR-012）下，成绩单 / 结课报告要拿给家长看 —— 数据必须经得起追问。
2. **一次设计，多处复用**：通用表 + 白名单，避免"N 个模块各写一套"（H6 的教训）。
3. **改动作本身要留痕**：反复修改是异常信号，可支撑内部风控。
4. **下游依赖已成事实**：成绩、课消、作业都在被看板与报告消费，源数据不可信则全盘不可信。
5. **成本落在数据层而非业务层**：集中在写入路径，业务代码改动小。

## 明确不做

- **不做**全表全字段的通用审计（只做**白名单字段**）
- **不做**数据版本快照 / 时光回溯（成本与收益不成比例）
- **不做**把 `audit_logs` 与 `data_change_logs` 合并（**一个是操作维度、一个是数据维度，语义不同**）
- **不做**让 `data_change_logs` 参与业务查询（它是**记录**，不是业务表）

## 影响

**数据层**
- 新增 `data_change_logs` 表（**新增迁移，版本号连续，当前基线 v20**）
- `exam_scores` 增加 `updated_at`；其余白名单表补齐时间戳
- 同步 `server/database.md`

**接口 / 前端**
- 成绩 / 课消 / 作业登记的编辑入口：需审批的场景增加**二次确认 + 原因填写**
- 新增"修改记录"查询端点（按 `table_name + record_id`）
- 成绩详情、课消流水、学员 360 增加**「修改记录」入口**

**横向同类扫描（强制）**
- ⚠️ 全量找出所有**直接覆盖式写入**的位置（批量导入、录分覆盖、课时回补）→ 统一接入留痕
- 批量导入场景：导入报告需包含"本次修改了 N 条历史数据"

## 复审条件

1. **记录量增长过快**（如导入大表导致日志膨胀）→ 评估对 `auto` / `import` 来源降采样
2. **"填原因"成为老师负担** → 扩大默认原因覆盖范围，或改为可选
3. **出现审计合规要求**（如需要独立导出审计报表）→ 评估独立报表模块
4. **性能下降**（写入路径同步写日志变慢）→ 评估异步落盘
