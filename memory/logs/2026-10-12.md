# 2026-10-12 · 学员档案 / 课时对账（v29 对账式扣课）两轮

## 10:00 | Decision | 扣课由「事件式」改为「对账式」

- 来源: 会话（用户报障「学生耗课后报班管理里课时剩余没变」）
- 根因: 旧扣课只在「考勤状态变化那一瞬间」执行，此刻匹配不到订单（无课时包/未报班/课程不符）即**永久漏扣且无提示**
- 影响: `server/src/utils/hours-reconcile.js`(新) · `migrations/029-*`(新) · attendance/finance/makeups/leaves/leads/students.js · 两个新页面
- 关联: ADR-003（剩余学费口径未动）

## 11:00 | Decision | 「已扣判定」必须按**条数净额**，不能按 SUM(hours)

- 来源: 会话（实测数据定调）
- 依据: 历史库「出勤考勤 ↔ 扣减流水」**条数严格一一对应**（黄子涵 8 对 8），但 `hours` 老口径=2 / 新口径=1
- 为什么不这么做: 按 hours 求和会把 8 条历史考勤误判为未扣 → **一次性重复扣 88 节课**
- 口径: `SUM(CASE WHEN type='扣减' THEN 1 ELSE -1 END) > 0`；已扣匹配两段式（精确 `attendance_id` / 宽松 `date` 兜底），宽松段刻意「宁可少补、绝不重复扣」
- 影响: `hours-reconcile.js` `DEDUCTED_EXISTS`

## 11:55 | Correction | 学员档案汇总卡「全 0」不是没数据，是**口径未在界面说明**

- 来源: 会话（用户实测截图反馈「这个学生已经耗课了，但是依然没有信息显示」）
- 真相: `summary` 只汇总 `status='在读'` 订单，而下方表格列**全部**订单 → 该学员唯一订单是退班 → 卡片全 0、表格有数，两边矛盾
- 决定: **主口径仍是「在读」（ADR-003 金额口径不得放宽）**，增补**全量口径**字段做对照，界面加口径说明条 —— 而不是改语义
- 影响: `students.js` summary 增补 `*_all` / `*_order_count`；`finance.js` 课消统计同理增补（**不改** `total_hours`/`remain_hours` 语义，因为「剩余课时分布」图也消费它，放宽会把已退班学员算进分布）

## 12:00 | Decision | 历史漏扣「真正补上」也走 API，不走原始 SQL

- 来源: 用户拍板（两轮 AskUserQuestion 共 6 项）
- 做法: `PUT /orders/189/status {在读}` —— **该接口本就内置自动对账**（finance.js:246-250）→ 自动补扣 → 再置回 `{退班}`
- 结果: 订单#189 总16/已耗1/剩15/退班，剩余学费 1000.01→937.51（ADR-003 重算），流水 `source=对账修正` + `attendance_id=746` 可追溯，幂等
- 为什么不这么做: 直接改库无审计、且违反 K-053 精神
- 例外: 删除考勤#748 走了**容器内 SQL**（后端与前端**都没有**删除考勤的入口），已标注为一次性操作

## 12:05 | Pitfall | UI 断言假阳性：读错了维度

- 现象: 课消统计页**默认维度是「按老师」**，我按「学号/姓名/班级」读前 3 列，实际读到的是「老师/班级/消耗课时」→ **3 条断言错误地变绿**
- 教训: 断言多维度页面的表格前，**必须先切换维度并断言当前维度**，再读列；否则列名对不上也会"通过"
- 关联: 与 K-081（注入式 UI 测试绕过真实链路）同类：**绿不等于对**

## 12:06 | Pitfall | 构建期间改了被 COPY 的源码

- 现象: `docker compose build` 启动后又改 `server/src/**` → 镜像里没有该改动
- 教训: 构建期间不要改源文件；发现后必须**重新构建一次**（层缓存命中时很快）
- 另: 本地 `vite build` 会被沙箱 shim 拦截（删 `dist/` 被拒）——**不要用**，正经路径是 `docker compose build unified`（容器内 `pnpm build`）
