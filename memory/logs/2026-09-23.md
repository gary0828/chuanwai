## 11:30 | Decision | 记忆系统升级方案（参考业界设计；用户已放宽体积约束）

- 来源: 会话（用户：「只要对开发有帮助，超一点空间没关系；目标是 **token 不浪费、效率最高**；参考其他项目的优秀设计给更新方案」）
- **调研结论（多来源一致，可作为依据）**
  1. **Progressive disclosure 分层加载**（Anthropic / vibehackers / penchan / thecolony）：
     L0 索引常载 → L1 工作记忆 → L2 主题文件按需 → L3 归档。实测只载索引 **<3KB vs 全载 ~15KB**；
     某案例会话启动 **4200 → 900 token**，加载内容使用率 84%
  2. **索引不是容器**：一行一个文件、细节外移到主题文件（像书目录，不读全书再找章节）
  3. **按文件模式条件加载**（Kiro `inclusion: fileMatch`）：改 `.tsx` 才加载 React 规则 → **确定性**省 token；
     另有 `always` / `auto`（按 description 匹配）/ `manual`（`#文件名` 显式调用）三档
  4. **提升管线**：日志 → 主题文件 → 索引，靠**有损压缩**沉淀；"大部分日志条目该死"是对的
  5. **反模式**：每会话全读、巨型 MEMORY.md、**逐字记流水账**、多源真相、存 `grep`/`git log` 能查到的东西
  6. **陈旧比没有更危险**：用前先验证（`grep`/`ls`），**代码当前状态永远赢过记忆**
  7. **不要上向量库**：<1 万条时文件方案准确率更高（72.9% vs 66.9%）且零基础设施
- **对照本项目**：骨架（INDEX / CURSOR / knowledge / logs / tasks / check.mjs）**本就接近最佳实践**；
