# 数据模型评审（Data Model Review）

本 Skill 用于**教务管理系统项目**（`server/` 后端 SQLite + node:sqlite，前端 pure-admin-thin + element-plus，部署于 Docker）。在新增/修改任何功能**之前**强制执行，防止跨模块数据关联性缺陷（双数据源、联动不完整、删除保护缺失、状态机无反向补偿、统计口径漂移）以及流程失控。

> **项目背景**：v1-v12 因未预先规划数据模型与开发流程，导致大量关联性问题（考勤↔请假不同步、用户/学生双数据源、删除级联清空历史等），v13 集中修复并沉淀本 Skill 作为预防机制。

## 行为准则（对用户需求的处理方式）

用户提出需求时，**先基于项目现状审核，再讨论**，不机械执行：

- 审核该功能与现有数据模型、跨模块联动、组件体系、既有测试的兼容性，目标是**准确实现且不产生额外困扰**
- 发现风险 → 向用户**风险提示**，附上我的方案
- 认为用户方案有问题 → 直接**指出并推翻**，同时**阐述替代方案**
- 最终由用户拍板；用户确认后按其决定执行

## 触发时机

在以下任一情况发生时**必须**调用（先走完 5 步流程，评审通过且用户确认后才允许写实现代码）：

- 用户提出新功能、新页面、新接口
- AI 侧提出任何功能设想（同样必须先过评审）
- 新增后端数据表 / 迁移脚本（`server/src/migrations/00N-*.js`）
- 给现有表加字段、改约束、改外键
- 新增或修改跨模块联动（考勤↔请假、财务↔订单、通知撤销等）
- 新增或修改删除逻辑（DELETE 接口）
- 新增或修改状态流转（审批、作废、撤销等）
- 修改统计报表 / 课消 / 经营报表的数据来源

## 开发流程（5 步）

普通改动（不涉及数据模型变更）全在对话内完成，不落盘文档；**只有 STEP 1 触发数据模型评审时才落盘**。

### STEP 0 需求评审（必要性闸门）

- 确认需求来源（用户提出 / AI 提出）
- 论证**必要性**：是否已有功能覆盖？是否重复建设？价值是否匹配复杂度？——按「行为准则」审核，有问题则风险提示或推翻
- 明确**范围与非目标**（明确不做哪些）
- 明确**验收点**（完成标准）
- 输出：简短结论，向用户确认后进入 STEP 1

### STEP 1 方案设计（用户确认闸门）

- **功能流程**：页面 / 接口 / 状态流转设计
- **前端组件**：只用 pure-admin 生态 + element-plus **官方组件**；禁止引入第三方 UI 库、禁止自造组件替代官方组件
- **后端实现**：路由设计、事务边界
- **数据库设计**：若有建表 / 加字段 / 改约束 → 进入下方「数据模型评审」子环节（4 工件 + 7 gate），并**落盘** `server/docs/`
- **联动规划**：列出受影响的数据与功能；跨模块联动必须设计**正向 + 反向补偿**（如正向回补课时，反向就重扣课时；正向发通知，反向撤通知）
- 输出：方案摘要 + 风险说明，**向用户确认后才允许进入实现（STEP 2）**

### STEP 2 用户确认

- 把方案（含必要性与联动影响）简明呈现给用户
- 用户明确确认后，才开始写代码；**未确认不得动手**

### STEP 3 分模块实现

- 一次只实现一个功能模块，禁止一次性生成全量代码
- 每个模块即时验证：lint / 构建 / 接口跑通（在 Docker 环境验证）
- 数据模型变更按「数据模型评审」要求逐步落地

### STEP 4 全流程测试 + 关联回归 + 提交

- **新功能 e2e 场景**：在 `server/scripts/e2e-lifecycle.mjs` 补充对应阶段与断言
- **关联模块回归**：涉及联动的改动必须重跑受影响模块的既有流程（如请假改动 → 重跑考勤全流程、补课、通知），确保老功能不被破坏（CRM 数据网状关联，此项为硬性要求）
- 运行完整 e2e 全流程，确认全部通过
- 更新文档（`server/database.md` 等）
- 提交；数据模型变更需评审文档且结论为「通过」（pre-commit 硬拦）

## 数据模型评审（STEP 1 的硬性子环节）

仅当本次变更涉及**建表 / 加字段 / 改约束 / 改外键**时触发，按以下原流程执行。

### 工件 1：数据模型变更单

列出本次变更涉及的表/字段/约束：

| 表 | 字段 | 类型 | NULL | 默认值 | CHECK | 外键(ON DELETE) | 唯一索引 |
|---|---|---|---|---|---|---|---|
| 示例: leaves | source | TEXT | NO | '手动' | IN ('手动','考勤同步') | - | - |

要点：
- 外键必须显式声明 ON DELETE 语义（CASCADE / RESTRICT / SET NULL），并说明理由
- 新建表的每条外键都要在「删除影响矩阵」中有对应条目

### 工件 2：数据源归属表

为每个共享/冗余字段明确**唯一数据源**：

| 字段 | 唯一写入口（表+接口） | 消费方（只读） | 是否冗余 | 冗余同步时机 |
|---|---|---|---|---|
| 示例: users.phone | users（用户管理） | 无 | 否（单一来源） | - |
| 示例: students.phone | students（学生档案） | users.phone 已弃用 | 是 | v13 已收敛 |

**硬性规则**：
- 一个业务字段只允许一个写入口；其余引用方一律 JOIN 读取，禁止复制存储
- 若确实需要冗余（如快照字段），必须声明同步时机与补偿逻辑，否则判为「双数据源」违规

### 工件 3：跨模块联动清单

为每个跨模块联动填写：

| 触发方（接口+动作） | 目标方（表+字段） | 方向 | 反向补偿 | 幂等性 | 事务边界 |
|---|---|---|---|---|---|
| 示例: attendance/batch 标记请假 | leaves 生成同步单 | 单向→ | 改回其他状态撤销同步单 | 已有覆盖单则不重复生成 | 同事务 |

要点：
- 状态机必须成对：每个正向转换，必须有明确的反向/补偿路径（驳回、撤销、改回）
- 反向补偿必须与正向对称（如正向回补课时，反向就重扣课时；正向发通知，反向删通知）
- 事务边界：跨表写必须 `db.exec("BEGIN")...COMMIT/ROLLBACK`

### 工件 4：删除影响矩阵

为每个新增/修改的删除逻辑填写：

| 删除对象 | 级联清理（表） | 应保护（RESTRICT，原因） | e2e 断言 |
|---|---|---|---|
| 示例: students | attendances/notifications/parent_children/exam_scores | orders（有报班记录禁止删） | 阶段6.2/6.3 |

要点：删除前必须先列出全部关联表，**有业务历史（订单/缴费/成绩）必须保护**，纯从表可级联。

## 强制检查清单（Gate）

以下 7 项全部通过才允许进入实现阶段。任何一项不通过 → 返回「不通过」结论并列出未满足项。

| # | 检查项 | 检查方式 | 违反后果 |
|---|---|---|---|
| G1 | 每个字段有唯一数据源，无双写 | 审查工件2 | 阻断 |
| G2 | 跨模块写操作单事务 | 审查工件3 | 阻断 |
| G3 | 状态机成对（正向必有反向补偿） | 审查工件3 | 阻断 |
| G4 | 删除有影响矩阵（保护/级联明确） | 审查工件4 | 阻断 |
| G5 | 联动幂等（重复触发无重复副作用） | 审查工件3 | 阻断 |
| G6 | 新表/新字段有版本化迁移 + 更新 `server/database.md` | 核对迁移目录 | 阻断 |
| G7 | 新联动有 e2e 场景覆盖（阶段编号） | 核对 `server/scripts/e2e-lifecycle.mjs` | 建议（涉及联动/删除/统计的功能视为必做） |

> G1-G6 为阻断项，G7 为建议项（但涉及联动/删除/统计的功能应视为必做）。

## 评审结论与落盘

1. 产出 4 工件 + gate 检查结果
2. 结论为「**通过**」或「**不通过**」，不通过时列出未满足的 gate 编号与修复要求
3. 将评审记录保存到 `server/docs/<迁移版本>-<功能名>-model-review.md`（迁移版本形如 `013`，无迁移时用 `none`），格式：

```markdown
# <功能名> 数据模型评审

- 日期：
- 变更类型：新增表 / 加字段 / 联动 / 删除逻辑 / 状态流转
- 结论：通过 / 不通过

## 1. 数据模型变更单
（表格）

## 2. 数据源归属表
（表格）

## 3. 跨模块联动清单
（表格）

## 4. 删除影响矩阵
（表格）

## Gate 检查结果
| Gate | 结果 | 说明 |
|---|---|---|
| G1 | ✅/❌ | ... |
...

## 未通过项与修复要求
（如有）
```

4. 评审通过并实现完成后，将 e2e 阶段号与迁移版本号补记到该文件「实现记录」小节

## Pre-commit 衔接

- 新迁移文件（`server/src/migrations/00N-*.js`）提交前，`husky pre-commit` 检查 `server/docs/` 下存在对应的 `<功能名>-model-review.md` 且结论为「通过」（`grep "结论：通过"`）
- 若缺失或未通过，提交被阻止，提示先运行本 Skill 完成建模评审

## 禁止事项

- 禁止在未完成 STEP 0/1 且用户未确认的情况下直接写代码
- 禁止引入第三方 UI 库，或自造组件替代 pure-admin / element-plus 官方组件
- 禁止新增/修改删除、状态流转、联动逻辑时不设计反向补偿
- 禁止涉及联动的改动不跑关联模块回归就直接提交
- 禁止在未产出 4 工件的情况下提交数据模型变更
- 禁止修改已发布的迁移脚本（`00N` 已执行过的只能新增 `00N+1`）
- 禁止在评审记录中写入敏感信息（凭据、真实学生数据等）
